# PR 작성

리뷰어가 PR 본문에서 알고 싶은 건 두 가지뿐입니다. **무엇이 바뀌었나**,
**그게 맞는지 어떻게 확인하나.** 나머지는 diff 를 보면 됩니다.

그래서 이 스킬은 사용자의 기억이 아니라 **diff 를 근거로** 씁니다. 사람이 쓴 PR 이
장황해지는 이유는 대개 "무엇을 했는지 떠올리며 쓰기" 때문이고, 그러면 한 게 아니라
하려던 게 적힙니다.

## 1. 무엇이 바뀌었는지 먼저 본다

본문을 쓰기 전에 실제 변경을 확인합니다. 이 순서를 뒤집지 마세요.

```bash
git branch --show-current
git log --oneline develop..HEAD
git diff develop...HEAD --stat
git diff develop...HEAD          # 양이 많으면 --stat 로 좁힌 파일만
```

여기서 얻은 것만 본문에 씁니다. diff 에 없는 것은 쓰지 않습니다.

## 2. 템플릿을 읽는다

```bash
cat .github/pull_request_template.md
```

소제목을 **그대로, 순서대로** 채웁니다. `<!-- -->` 주석의 지시(제목 형식, 300줄 기준)도
함께 지킵니다. 선택 항목(스크린샷/로그)은 넣을 게 없으면 비워 두세요 — 억지로 채운
"해당 없음" 은 읽는 시간만 씁니다.

**관련 이슈**는 브랜치 이름에서 번호를 꺼냅니다. `feature/127-unify-handler-response`
→ `Closes #127`. 브랜치에 번호가 없으면 사용자에게 물어보세요.

## 3. 작성 원칙

**소제목 하나 = 질문 하나에 대한 답.**

| 소제목 | 답해야 할 질문 |
|---|---|
| 변경 사항 요약 | 무엇이 어떻게 바뀌었나 |
| 작업 체크리스트 | 이 PR 이 실제로 해낸 항목은 무엇인가 |
| 테스트 / 검증 방법 | 리뷰어가 뭘 돌려보면 확인되나 |

지켜야 할 것:

- **각 소제목 본문 200자 이내** (공백 포함, **산문 기준**). 코드블록과 백틱으로 감싼
  경로·함수명은 세지 않습니다 — 제한은 장황한 말을 잡으려는 것이지 복붙 가능한 명령을
  지우게 하려는 게 아닙니다. 넘으면 내용이 아니라 군더더기를 지웁니다.
- **파일 경로로 말한다.** "데이터를 적재하는 부분의 로직을 일부 수정" 대신
  `gas_price_bronze_to_silver/loader.py` 를 씁니다. 리뷰어가 바로 그 파일을 엽니다.
- **왜 바꿨는지는 한 줄이면 충분하다.** 배경이 길어야 이해되는 변경이면 그건 PR 이
  큰 것이지 설명이 부족한 게 아닙니다. 분리를 검토하세요.
- **검증 방법은 복붙 가능한 명령으로.** "테스트 완료" 는 리뷰어가 할 수 있는 게 없습니다.
- **체크리스트는 한 줄 한 항목, 실제로 한 것만.** 안 한 걸 미리 체크하지 않습니다.
- **다짐·사과를 넣지 않는다.** "부족한 부분은 리뷰 부탁드립니다" 는 정보가 0입니다.
- **한 문단 = 한 줄. 문단을 80자에서 끊지 않는다.** GitHub 은 문단 안의 단일 줄바꿈도
  그대로 줄바꿈으로 표시합니다. 하드랩하면 조사가 줄을 넘어가 문장이 토막나 보입니다.
  줄바꿈은 **문단 사이와 목록 항목 사이에만** 넣고, 목록 항목도 한 줄로 끝냅니다.
- **문체는 명사형 종결 또는 음슴체.** PR 본문에 존댓말을 쓰지 않습니다.
  종결어미가 짧아지는 것보다 중요한 건, "~하는 것이 좋을 것 같아 진행했습니다" 같은
  완충 표현을 쓸 자리가 사라져서 무엇을 했는지가 또렷해진다는 점입니다.

  | 쓰지 않음 | 씀 |
  |---|---|
  | 구조를 리팩토링했습니다 | `pipeline_core` 구조로 리팩토링 |
  | 상수 참조를 수정하였습니다 | 상수 참조 복구 |
  | 테스트가 통과하는 걸 확인했습니다 | 51 passed 확인 |
  | 추후 개선이 필요해 보입니다 | 개선은 후속 이슈로 분리 |

  제목도 같습니다 — `fix(lambda): gas price 핸들러 상수 참조 복구`.

### 예시

## 4. 등록 전에 검사한다

```bash
python3 .claude/skills/write-issue/check_draft.py <초안.md>
```

200자를 넘은 소제목과 문단 중간에서 끊긴 줄을 행 번호로 알려줍니다.
통과(exit 0)할 때까지 고치세요. (스크립트는 `write-issue` 쪽에 하나만 둡니다.)

## 5. 확인받고 올린다

초안을 사용자에게 보여주고 **승인을 받은 뒤** 올립니다. PR 은 팀원에게 알림이 가는
외부 산출물입니다.

올리기 전 확인:

```bash
git status                       # 커밋 안 된 변경이 남아 있지 않은지
git push -u origin HEAD          # 원격에 브랜치가 있어야 PR 이 생성됩니다
command -v gh >/dev/null || brew install gh    # brew 가 없으면 https://cli.github.com 안내
gh auth status
```

`gh auth status` 가 "not logged into any GitHub hosts" 를 뱉으면 **직접 `gh auth login`
을 실행하지 마세요.** 브라우저 인증이 필요한 대화형 명령이라 세션이 멈춥니다.
사용자에게 프롬프트에 `! gh auth login` 을 입력해 달라고 요청하세요.

```bash
gh pr create \
  --base develop \
  --title "fix(lambda): gas price 핸들러 상수 참조 복구" \
  --body-file <초안.md>
```

- **`--base develop` 이 기본입니다.** 일반 작업 브랜치를 `main` 으로 바로 올리지
  않습니다 (팀 Branch 규칙). `main` 으로 가는 건 hotfix 뿐이고, 그때는 사용자에게
  확인받으세요.
- 제목은 Conventional Commits 형식 — `type(scope): subject`.
- 올린 뒤 PR URL 을 사용자에게 알려주세요.
