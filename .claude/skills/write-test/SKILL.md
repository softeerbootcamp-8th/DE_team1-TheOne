# 테스트 작성

팀 규칙상 완료 조건은 "돌려볼 수 있는 것"이어야 합니다. 그런데 테스트는 **쓰기는 쉽고
의미를 갖기는 어렵습니다.** 함수를 부르고 반환값이 `None` 이 아닌지 보는 테스트는
초록불을 켜 주지만 아무것도 막지 못하고, 오히려 "검증됨"이라는 착각을 남깁니다.

그래서 이 스킬은 순서를 뒤집습니다. **코드를 보고 테스트를 쓰는 게 아니라, 이 기능이
어떻게 틀릴 수 있는지를 먼저 나열하고 그중 무엇을 붙잡을지 정한 다음 씁니다.**
시나리오가 먼저이고 코드가 나중입니다.

## 1. 무엇이 바뀌었는지 확인한다

추측으로 테스트를 쓰면 존재하지 않는 함수를 부르거나 이미 있는 테스트를 다시 씁니다.
먼저 실제 변경을 봅니다.

```bash
git status
git diff --stat develop...HEAD    # 브랜치 작업이면
git diff                          # 아직 커밋 전이면
```

그리고 **이미 있는 테스트를 반드시 읽으세요.** 같은 데이터셋의 테스트 파일이 있으면
그게 이 저장소의 관례이자 이미 커버된 범위입니다. 중복해서 쓰면 유지비만 늘어납니다.

```bash
ls lambda/tests/functions/ libs/pipeline_core/tests/ spark/tests/ airflow/tests/ 2>/dev/null
```

**사용자가 말한 변경이 저장소에 없으면 그 사실을 알리세요.** "이거 고쳤어" 로 시작하는
요청인데 `git diff` 에 그 변경이 없는 경우가 실제로 있습니다 — 다른 브랜치에서 했거나,
하려다 말았거나, 이미 되돌렸거나. 이때 **말없이 대신 고치지 마세요.** 사용자는 자기 코드가
그 상태라고 믿고 있고, 내가 조용히 고쳐 버리면 그 착각이 유지된 채 diff 만 커집니다.
"말씀하신 변경이 저장소에 없습니다. 제가 넣을까요, 아니면 다른 브랜치인가요?" 를 먼저
물으세요.

## 경계 — 이 스킬은 테스트를 씁니다, 구현을 고치지 않습니다

경계를 미리 그어 둡니다. 테스트를 쓰다 보면 구현을 손보고 싶어지는데, 두 가지가 섞이면
문제가 생깁니다.

**내가 방금 고친 동작에 테스트를 쓰면 그 테스트는 아무것도 검증하지 않습니다.** 구현과
테스트를 같은 머릿속에서 같은 시각에 만들었으니 당연히 일치합니다. 회귀를 막아 주지도
않고 — 애초에 그 회귀는 존재한 적이 없습니다 — 대신 "검증됨" 이라는 착각만 남습니다.

그래서 테스트를 쓰다 구현 문제를 발견하면:

1. **테스트로 고정합니다.** 실제 동작을 기술하는 테스트를 쓰고, 그게 바람직하지 않은
   동작이면 `pytest.mark.xfail(reason="...", strict=False)` 로 사유와 이슈 번호를 남깁니다.
   이러면 나중에 고쳐졌을 때 알 수 있고, 문제가 코드에 기록됩니다.
2. **사용자에게 보고합니다.** 무엇이 문제이고 왜 문제인지. 고치는 건 사용자의 결정입니다.
3. 사용자가 "그럼 고쳐줘" 라고 하면 그때 고칩니다.

예외는 4단계의 고의 파괴 검증뿐이고, 그건 반드시 원복합니다.

## 2. 시나리오를 먼저 뽑는다

여기가 이 스킬의 전부입니다. 코드를 한 줄도 쓰기 전에, **이 기능이 조용히 틀릴 수 있는
방식**을 나열합니다.

아래 8개 렌즈를 순서대로 대 보세요. 데이터 파이프라인에서 실제로 사고가 나는 지점들이고,
오른쪽 칸은 이 저장소에서 실제로 있었던 일입니다. 남의 얘기가 아니라는 뜻입니다.

| 렌즈 | 물어볼 것 | 이 저장소의 실제 사례 |
|---|---|---|
| **계약** | 반환 스키마와 저장 위치가 약속대로인가 | `WriteResult.location` 이 layout 이 정한 경로와 같은가 |
| **멱등성** | 같은 입력을 두 번 넣으면 어떻게 되나 | HVFHV 재수집분이 중복 집계됨 (`docs/issue-report.md` 1번) |
| **경계 데이터** | 0건 / 1건 / 결측 / 원본이 전부 문자열일 때 | 제원 원본이 "해당 없음"을 `"0"` 으로 채워 보냄 |
| **실패의 격리** | 일부가 깨졌을 때 나머지는 살아남나 | 과거 파티션이 깨져도 당일 처리는 성공해야 함 |
| **실패의 노출** | 조용히 통과하면 안 되는 것이 통과하나 | 대상 날짜를 처리 안 했는데 이전 실행이 남긴 파일 때문에 통과 |
| **계약 위반** | 잘못된 입력을 명시적으로 거부하나 | `collected_date` 와 `collected_month` 를 둘 다 지정 |
| **경계 넘김** | 쓰는 쪽과 읽는 쪽이 같은 규칙을 보나 | Bronze writer 와 Silver reader 가 같은 layout 모듈을 봐야 함 |
| **상류 변화** | 원본이 바뀌면 터지나 조용히 통과하나 | TLC 가 컬럼을 바꿔도 Bronze 는 통과하고 Spark 에서야 터짐 |

전부 적용할 필요는 없습니다. 순수 계산 함수에 멱등성 렌즈를 대는 건 낭비입니다.
해당 없으면 넘어가되, **넘어갔다는 걸 알고 넘어가세요.**

### 시나리오를 거르는 기준

각 시나리오마다 한 문장으로 답하세요 — **"이 테스트가 없으면 어떤 버그가 통과하나?"**

답을 못 대면 그 시나리오는 지웁니다. 이게 단순한 테스트를 막는 유일한 장치입니다.
줄 커버리지 숫자는 이 질문에 답해 주지 않습니다. 실행됐다는 것과 검증됐다는 것은
다른 얘기이고, 우리가 원하는 건 후자입니다.

나쁨 — 막는 버그를 못 댐:

> `extract()` 가 리스트를 반환하는지 확인
> → 리스트가 아니면 다음 줄에서 어차피 터집니다. 이 테스트가 잡는 버그가 없습니다.

좋음 — 막는 버그가 분명함:

> 연식 묶음이 두 개인 모델이 두 행으로 펼쳐지는지 확인
> → 펼치기 로직이 첫 묶음만 읽으면 조용히 데이터의 절반이 사라집니다.

### 사용자에게 보여주고 승인받는다

시나리오 표를 그대로 보여주고 확인받으세요. 테스트를 다 쓴 뒤에 "이건 필요 없는데요"
소리를 듣는 것보다 훨씬 쌉니다. 사용자가 도메인을 더 잘 알기도 하고요.

```
| # | 시나리오 | 이게 없으면 통과하는 버그 |
|---|---|---|
| 1 | 정상 수집 → 파티션 경로/행수 | layout 규칙과 어긋난 경로에 써도 모름 |
| 2 | 같은 날 재수집 | 재수집분이 덮어써서 스냅샷 이력이 사라짐 |
| 3 | OCR 실패 행 | 한 행 실패로 파이프라인 전체가 죽음 |
| 4 | 빈 응답 | 0건을 정상으로 적재해 Silver 가 빈 값을 물려받음 |
| ~~5~~ | ~~응답이 리스트인지~~ | ~~막는 버그 없음 — 제외~~ |
```

커버하지 **않기로** 한 것도 사유와 함께 남기세요. 나중에 "왜 이건 없지" 를 다시 묻지
않게 됩니다.

## 3. 테스트를 쓴다

### 어디에 쓰고 어떻게 돌리나

| 대상 | 테스트 위치 | 실행 |
|---|---|---|
| Lambda 핸들러/Extractor/Loader | `lambda/tests/functions/test_<dataset>_*.py` | `cd lambda && uv run --frozen pytest` |
| `pipeline_core` 인터페이스 | `libs/pipeline_core/tests/` | `cd libs/pipeline_core && uv run --frozen pytest` |
| Spark Transformer/job | `spark/tests/` | `cd spark && uv run --frozen pytest` |
| Airflow DAG | `airflow/tests/` | `cd airflow && uv run --frozen pytest` |

`spark/tests/` 와 `airflow/tests/` 는 아직 없습니다. **이 스킬은 두 곳의 경로와 실행
명령까지만 안내하고, 세션 픽스처나 DAG 로딩 골격은 다루지 않습니다.** Spark 는 JVM 이
필요하고 Airflow 는 DAG 파싱 방식이 버전마다 달라서, 골격을 여기 적어 두면 틀린 채로
굳습니다. 두 런타임의 첫 테스트를 만들 차례가 되면 그때 확인해서 쓰고, 자리가 잡히면
별도 참조 문서로 분리하세요.

그 전까지 Spark·Airflow 테스트를 쓸 때도 아래 규칙(CI 조건, 작성 관례, 4단계 검증)은
그대로 적용됩니다. 특히 실행 환경이 안 갖춰져 돌려볼 수 없다면 4단계의 「돌릴 수 없을 때」
를 반드시 따르세요 — 이 저장소에서 실제로 통과 불가능한 Spark 테스트가 나온 경로입니다.

### CI 에서 돌 수 있어야 한다

테스트가 로컬에서만 통과하면 CI 는 아무것도 지켜 주지 못합니다. CI 러너에는 네트워크
접근을 신뢰할 수 없고, 시계가 다르고, `tesseract` 같은 시스템 바이너리가 없을 수 있고,
`~/data` 같은 경로도 없습니다.

- **네트워크를 타지 않는다.** `fetch` 만 `monkeypatch` 로 대체하고 파싱·변환은 진짜를
  돌립니다. 파싱까지 대체하면 검증 대상이 사라져 테스트가 자기 자신을 확인하게 됩니다.

  ```python
  monkeypatch.setattr(extractor, "fetch", lambda city_slug, timeout: PAYLOAD)
  ```

- **시각을 고정한다.** `datetime.now()` 가 테스트 안에서 불리면 파티션 경로가 매일
  달라집니다. 수집 시각은 상수로 만들어 주입하세요 (`COLLECTED_AT = datetime(2026, 8, 10, 3, 0, tzinfo=timezone.utc)`).
- **파일은 `tmp_path` 에만 쓴다.** 저장소 안이나 `~/` 에 쓰면 CI 에서 권한/경로로 깨지고,
  로컬에서는 이전 실행 잔여물 때문에 통과합니다.
- **외부 바이너리에 기대지 않는다.** `tesseract` 가 필요한 단계는 그 단계 입력을 직접
  넣어 우회합니다. `pytest.importorskip` 으로 건너뛰면 CI 에서 조용히 아무것도 안 돕니다.
- **테스트끼리 순서에 기대지 않는다.** 각 테스트는 자기 `tmp_path` 안에서 자기 fixture 를
  만듭니다.

### 이 저장소의 작성 관례

기존 테스트 파일을 열어 보면 바로 보이지만, 요약하면:

- **테스트 이름은 한글 서술형.** `test_같은_날_다시_받아도_덮어쓰지_않는다` 처럼 이름만
  읽고 무엇을 보장하는지 알 수 있게 씁니다. `test_loader_1` 은 실패했을 때 아무 정보도
  주지 않습니다. (`libs/pipeline_core/tests/` 는 영어를 쓰고 있으니 그쪽은 영어로.)
- **파일 맨 위 docstring 에 시나리오 목록을 남깁니다.** 2단계에서 승인받은 표가 여기로
  옵니다. 리뷰어가 코드를 읽기 전에 무엇을 보장하는지 알게 되고, 나중에 시나리오가
  늘어날 때 여기부터 봅니다.

  ```python
  """vehicle_catalog Raw -> Bronze 적재 시나리오 (네트워크 없이 fetch 만 대체).

  1. 정상 수집 → layout 이 정한 파티션 경로와 행 수
  2. 같은 날 재수집 → 이전 파일을 덮어쓰지 않음
  3. OCR 실패 행 → 가격만 None, 나머지 행은 그대로 적재
  4. 빈 응답 → RuntimeError 로 명시적 실패
  """
  ```

- **fixture 는 실제 원본의 모양을 따릅니다.** 편하게 만든 가짜 데이터로 통과하는 테스트는
  실제 데이터에서 깨집니다. 원본이 값을 전부 문자열로 주면 fixture 도 문자열이어야 합니다.
- **한 테스트 = 한 시나리오.** assert 를 여러 개 쓰는 건 괜찮지만, 서로 다른 시나리오를
  한 함수에 몰면 앞에서 실패했을 때 뒤가 안 돌아 정보가 반만 나옵니다.
- **검증은 결과의 의미까지 봅니다.** 파일이 생겼는지만 보지 말고 읽어서 내용을 확인하세요.
  경로만 맞고 내용이 깨진 경우가 실제로 가장 흔합니다.

  ```python
  written = pq.ParquetFile(result.location).read().to_pylist()
  assert {row["make"] for row in written} == {"Acura", "Kia"}
  ```

## 4. 테스트가 실제로 잡는지 확인한다

**초록불만 확인하고 끝내면 안 됩니다.** 아무것도 검증하지 않는 테스트도 초록불이 켜집니다.
쓴 테스트가 진짜 그물인지 보려면 구멍을 뚫어 봐야 합니다.

1. 테스트를 돌려 통과를 확인합니다.
2. **구현을 한 군데 고의로 깨뜨립니다.** 조건을 뒤집거나, 파티션 키를 바꾸거나,
   덮어쓰기 방지 분기를 지웁니다.
3. 해당 테스트가 **빨간불로 바뀌는지** 봅니다. 그대로 통과하면 그 테스트는 그 동작을
   검증하지 않는 것이므로 다시 씁니다.
4. 구현을 원상복구하고 다시 통과를 확인합니다.

시나리오마다 다 할 필요는 없고, **핵심 시나리오 1~2개만** 해 보면 충분합니다. 대개
거기서 "아, 이 assert 는 통과 여부와 무관했구나" 가 드러납니다.

구현을 되돌리는 걸 잊지 마세요. `git diff` 로 마지막에 확인합니다.

### 돌릴 수 없을 때

JDK 가 없어서 Spark 세션이 안 뜨거나, 필요한 의존성이 없거나, 환경이 갖춰지지 않아
테스트를 실행할 수 없는 경우가 있습니다. 이때 **"못 돌렸습니다" 라고 정직하게 보고하는
것만으로는 부족합니다.** 정직한 보고가 붙은 틀린 테스트는 여전히 틀린 테스트이고,
다음 사람은 그게 검증됐다고 믿고 넘어갑니다.

실행할 수 없으면 **구현 파일을 열어 assert 를 한 줄씩 대조하세요.** 실행이 잡아 주던
일을 손으로 대신하는 것이고, 실제로 여기서 대부분 걸립니다.

| 대조할 것 | 왜 여기서 틀리나 |
|---|---|
| 에러 메시지 정규식 | `f"{0.5:.2%}"` 는 `"50.00%"` 입니다. `match=r"50\.0%"` 는 매치되지 않습니다. 포맷 지정자를 눈으로 확인하세요 |
| 연산 순서 | "결측을 채운 뒤 검증" 인지 "검증한 뒤 채움" 인지. 구현에서 두 줄의 위치를 직접 보세요 — 순서를 거꾸로 가정하면 통과할 수 없는 테스트가 됩니다 |
| 시그니처와 키워드 이름 | 생성자가 그 키워드를 정말 받나. 기본값이 얼마인가 |
| 비교 연산자 | 임계치가 `>` 인가 `>=` 인가. 경계값 시나리오의 기대가 여기서 갈립니다 |
| 반환 컬럼·키 이름 | 파생 컬럼 이름을 추측하지 말고 구현에서 확인하세요 |

그리고 보고할 때 **"테스트를 추가했습니다" 가 아니라 "작성했으나 미검증" 이라고 쓰세요.**
무엇이 있어야 돌릴 수 있는지도 같이 알려 주세요 (예: `brew install --cask temurin`).
사용자가 그 한 줄을 실행하면 검증이 끝나는데, "추가했습니다" 로 적으면 아무도 돌리지
않습니다.

## 5. 보고한다

사용자에게 다음을 알립니다.

- 커버한 시나리오와 대응하는 테스트 이름
- 커버하지 않기로 한 것과 그 사유
- 4단계에서 무엇을 깨뜨려 봤고 어떤 테스트가 잡았는지
- **실행 여부** — 돌려서 통과한 것과, 작성했으나 미검증인 것을 섞지 말고 나누어 쓰세요
- 실행 명령 (사용자가 직접 돌려볼 수 있게)
- 테스트를 쓰다 발견한 구현 문제 (「경계」절에 따라 고치지 않고 보고만)

그리고 **이 저장소의 CI 는 `test` job 에서 `make test` 를 돌립니다**
(`.github/workflows/ci.yml`). 방금 쓴 테스트는 PR 에서 자동으로 실행되고, 깨지면 머지가
막힙니다 — 로컬에서 통과한 뒤 올리세요.

CI 설정 변경은 팀 전체에 영향을 주므로 이 스킬에서 임의로 하지 않습니다. 사용자가
"CI 를 바꿔줘" 라고 명시하면 그때 진행하세요.
