# 이슈 작성

팀 규칙상 **모든 작업은 이슈부터** 만듭니다. 문제는 사람마다 쓰는 모양이 달라
리뷰어가 "그래서 뭘 하겠다는 거지"를 두 번 읽어야 알게 된다는 것입니다.

이 스킬의 목표는 하나입니다. **읽는 사람이 한 번에 무엇을 왜 하는지 알게 하는 것.**
길이 상한(소제목당 200자)은 그걸 강제하는 장치일 뿐이고, 진짜 기준은 "군더더기 없이
필요한 사실만 있는가" 입니다.

## 1. 템플릿을 먼저 읽는다

레포의 템플릿이 유일한 기준입니다. 외우지 말고 매번 읽으세요 — 팀이 고칠 수 있습니다.

```bash
ls .github/ISSUE_TEMPLATE/
```

- **버그** (이미 있는 동작이 잘못됨) → `.github/ISSUE_TEMPLATE/bug.md`
- **그 외 전부** (기능·리팩터·문서·테스트·설정) → `.github/ISSUE_TEMPLATE/task.md`

템플릿의 소제목을 **그대로, 순서대로** 씁니다. 임의로 추가하거나 빼지 마세요.
`<!-- -->` 주석 안의 지시(제목 형식, 라벨, 크기 기준)도 함께 지킵니다.

## 2. 사실을 모은다

### 먼저 이미 있는 이슈인지 본다

**초안을 쓰기 전에 조회합니다.** 여기가 가장 싼 지점입니다 — 다 쓰고 등록한 뒤에
중복인 걸 알면 닫는 수고에 더해, 번호가 둘로 갈린 흔적이 보드에 남습니다.

```bash
gh issue list --state open --limit 50
gh issue list --state all --search "<핵심 키워드>" --limit 20
```

닫힌 것도 함께 봅니다. 같은 문제가 이미 처리됐다면 지금 쓰려는 건 새 이슈가 아니라
**회귀**이고, 그 사실이 이슈 본문에 들어가야 합니다 (어느 커밋에서 되살아났는지가
가장 중요한 단서입니다).

| 찾은 것 | 할 일 |
|---|---|
| 같은 일의 열린 이슈 | **발행하지 않습니다.** 그 번호와 제목을 사용자에게 알리고 판단을 받으세요 |
| 같은 일의 닫힌 이슈 | 회귀로 씁니다. 본문에 그 번호와 "재발" 을 명시 |
| 비슷하지만 범위가 다름 | 후보를 제시하고 사용자에게 물어보세요 |
| 관련만 있음 | 새로 발행하고 "참고 자료 / 관련 이슈" 에 그 번호를 적습니다 |
| 없음 | 새로 발행 |

"같다" 를 넉넉하게 판정하지 마세요. 제목이 비슷해도 손대는 파일과 완료 조건이 다르면
다른 이슈입니다. 반대로 제목이 달라도 같은 파일을 같은 이유로 고치는 것이면 같은
이슈입니다 — 판단 기준은 제목이 아니라 **범위**입니다.

`gh` 인증이 안 되어 조회가 막히면 그 사실을 알리고 사용자에게 확인을 요청하세요.
조회를 건너뛰고 발행하지 마세요.

### 그다음 내용을 확인한다

사용자 말만으로 부족하면 **직접 확인하고 씁니다.** 이슈에 들어가는 파일 경로·함수명·
동작은 추측이 아니라 확인된 것이어야 합니다. 틀린 경로 하나가 이슈 전체의 신뢰를 깎습니다.

- 관련 파일/함수를 찾아 실제 경로를 확보 (`lambda/functions/.../handler.py:28` 형태)
- 버그면 재현 명령을 실제로 돌려보고 그 출력·에러 메시지를 씁니다
- 확인 못 한 것은 쓰지 말고, 꼭 필요하면 "확인 필요" 라고 명시

## 3. 작성 원칙

**소제목 하나 = 질문 하나에 대한 답.** 그 소제목이 답해야 할 질문에서 벗어나면 지웁니다.

| 소제목 | 답해야 할 질문 |
|---|---|
| 작업 목적 | 지금 무엇이 문제라서 이걸 하나 |
| 완료 조건 | 무엇을 보면 끝났다고 판단하나 |
| 재현 절차 | 어떻게 하면 남도 똑같이 겪나 |
| 기대 / 실제 동작 | 무엇이 나와야 하는데 무엇이 나오나 |

지켜야 할 것:

- **각 소제목 본문 200자 이내** (공백 포함, **산문 기준**). 코드블록과 백틱으로 감싼
  경로·함수명·에러명은 세지 않습니다 — 제한은 "말이 장황한 것"을 잡으려는 것이지
  정확한 명령어를 지우게 하려는 게 아니기 때문입니다. 넘으면 내용을 자르지 말고
  **군더더기를** 지우세요. 대개 배경 설명과 다짐이 절반입니다.
- **경로와 이름으로 대체한다.** "가스 가격을 처리하는 람다 핸들러의 반환값 부분"은
  `gas_price_raw_to_bronze/handler.py:28` 한 줄이면 끝납니다. 문장 세 개가 사라집니다.
- **완료 조건은 검증 가능하게.** "잘 동작한다"가 아니라 돌려볼 명령, 통과할 테스트,
  비교할 수치로 씁니다. 체크박스는 한 줄에 하나, 각각 독립적으로 판정 가능해야 합니다.
- **다짐·사과·포부를 넣지 않는다.** "꼼꼼히 확인하겠습니다", "혹시 놓친 부분이 있다면"
  같은 문장은 정보가 0입니다.
- **한 문단 = 한 줄. 문단을 80자에서 끊지 않는다.** GitHub 이슈/PR 렌더러는 문단 안의
  단일 줄바꿈도 그대로 줄바꿈으로 표시합니다. 에디터에서 보기 좋으라고 하드랩하면
  조사가 줄을 넘어가(`docker compose up -d` / `가 실패했고`) 문장이 토막나 보입니다.
  줄바꿈은 **문단 사이와 목록 항목 사이에만** 넣고, 목록 항목도 한 줄로 끝냅니다.
- **문체는 명사형 종결 또는 음슴체.** 이슈 본문에 존댓말을 쓰지 않습니다.
  종결어미가 짧아지면 문장당 3~5자가 빠지고, 무엇보다 "~하는 것이 좋을 것 같다고
  판단했습니다" 같은 완충 표현을 쓸 자리가 사라져서 주장이 또렷해집니다.

  | 쓰지 않음 | 씀 |
  |---|---|
  | 리팩토링을 진행하려고 합니다 | `pipeline_core` 구조로 리팩토링 |
  | 핸들러가 죽는 문제가 있습니다 | 핸들러가 `NameError` 로 죽음 |
  | 테스트를 추가했습니다 | 회귀 테스트 1개 추가 |
  | 확인이 필요할 것 같습니다 | 확인 필요 |

  제목도 같습니다 — `[Bug] gas_price 핸들러가 NameError 로 죽음`.

## 4. 등록 전에 검사한다

눈대중으로 200자를 세거나 줄바꿈을 훑지 마세요. 초안을 파일로 쓴 뒤 돌립니다.

```bash
python3 .claude/skills/write-issue/check_draft.py <초안.md>
```

200자를 넘은 소제목과 문단 중간에서 끊긴 줄을 행 번호로 알려줍니다.
통과(exit 0)할 때까지 고치세요.

## 5. 확인받고 등록한다

초안을 사용자에게 보여주고 **승인을 받은 뒤** 등록합니다. 이슈는 팀 전체가 보는
외부 산출물이라 되돌리기 번거롭습니다.

등록 직전에 2단계의 조회를 했는지 확인하세요. 대화가 길어지면 초안을 고치는 데 집중해
조회를 건너뛴 채 여기까지 오게 됩니다. 안 했으면 지금 하고, 중복이면 등록하지 마세요.

`gh` 가 없으면 먼저 깝니다:

```bash
command -v gh >/dev/null || brew install gh    # brew 가 없으면 https://cli.github.com 안내
gh auth status
```

`gh auth status` 가 "not logged into any GitHub hosts" 를 뱉으면 **직접 `gh auth login`
을 실행하지 마세요.** 브라우저 인증이 필요한 대화형 명령이라 세션이 멈춥니다.
대신 사용자에게 프롬프트에 `! gh auth login` 을 입력해 달라고 요청하고, 끝나면
이어서 진행합니다.

등록:

```bash
gh issue create \
  --title "[Bug] gas_price 핸들러가 NameError 로 죽음" \
  --body-file <초안.md> \
  --label fix
```

라벨은 템플릿 주석 기준으로 답니다 — `feature` / `refactor` / `docs` / `test` /
`chore` 중 하나, 버그는 `fix`. 등록 후 반환된 이슈 URL 과 번호를 사용자에게 알려주세요
(다음 단계인 브랜치 이름과 PR 의 `Closes #` 에 그 번호가 들어갑니다).
