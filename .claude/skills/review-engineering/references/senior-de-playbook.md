## 1. 멱등성 — 재실행이 값을 바꾸지 않게

파이프라인 사고의 대부분은 로직 오류가 아니라 **같은 데이터를 두 번 처리한 것**입니다.
재시도, 수동 재실행, 백필이 전부 이 경로입니다.

구현 방식은 세 가지뿐이고, 고르는 기준은 "무엇을 덮어쓸 수 있는가" 입니다.

| 방식 | 조건 | 주의 |
|---|---|---|
| 파티션 덮어쓰기 | 파티션 키 = 데이터의 자연 키 | Spark 는 `partitionOverwriteMode=dynamic` 이어야 대상 파티션만 지움. static 은 전체를 지움 |
| 키 기준 upsert | 행 단위 자연 키가 있음 | Parquet 파일에는 upsert 가 없음 → 읽고 합쳐 다시 쓰기 |
| 읽을 때 중복 제거 | 원본 이력을 보존해야 함 | 읽는 쪽 전부가 규칙을 알아야 함. 잊으면 조용히 두 배 |

**판단선**: 쓰기 경로마다 "같은 입력으로 두 번 돌리면 행 수가 같은가" 에 답이 있어야
합니다. 답이 코드에 없고 사람의 기억에 있으면 부족입니다.

이 저장소의 재발 유형: Bronze 를 수집일로 파티션하고 월 단위 데이터를 담아 재수집분이
합산되는 경우, Silver Loader 가 static overwrite 로 이전 파티션까지 지우는 경우.

## 2. 파티션 설계

파티션 키는 **읽는 쪽의 필터**와 **쓰는 쪽의 재실행 단위**를 동시에 정합니다.
둘이 다르면 하나를 포기하게 되므로, 먼저 어느 쪽이 더 비싼지 정합니다.

- 파티션 하나당 목표 파일 크기는 **수백 MB 단위**. 수 MB 파일이 수천 개면(작은 파일 문제)
  S3 요청 수와 Spark 태스크 수가 파일 수에 비례해 늘어 읽기가 느려지고 비용이 붙습니다
- 파티션 카디널리티는 낮게. `collected_date` + `city` 처럼 두 단계면 충분하고, 여기에
  시각·차종 같은 축을 더하면 파티션이 폭발합니다
- 파티션 키는 값으로도 남기는 편이 안전합니다. 디렉터리 이름에만 있으면 파일을 옮기거나
  단일 파일을 읽었을 때 정보가 사라집니다
- **파티션 키를 바꾸는 것은 되돌리기 어려운 결정**입니다. 기존 데이터 이관 + 읽는 쪽 전부
  수정이 따라옵니다. 실측 근거를 만들고 결정 문서에 남기세요

## 3. 스키마 진화

깨지는 순서는 항상 같습니다 — 컬럼 추가는 안전하고, 삭제·이름 변경·타입 축소는 읽는 쪽을
조용히 부숩니다.

- **추가만 허용**을 기본 규칙으로. 새 컬럼은 nullable, 기존 행은 null 로 남깁니다
- 이름 변경은 "추가 + 병행 기간 + 삭제" 3단계. 한 번에 바꾸면 그 사이에 돈 잡이 죽습니다
- 타입은 넓히는 방향만(int32 → int64, date → timestamp). 좁히면 과거 데이터가 안 읽힙니다
- 기대 스키마를 코드에 상수로 두고 적재 후 대조하면(이 저장소의 `SCHEMA` + `schema_validator`)
  원천이 조용히 컬럼을 바꿨을 때 그날 알게 됩니다. 이게 없으면 분기 마감에 압니다

**판단선**: 스키마 변경 PR 에는 "이 컬럼을 읽는 곳" 목록이 있어야 합니다. `rg` 로 세면
끝나는 일이고, 세지 않은 스키마 변경은 부족입니다.

## 4. 백필과 재처리

- 처리 대상 기간은 **항상 파라미터**로. `today()` 를 코드 안에서 부르면 과거를 다시 돌릴
  방법이 사라집니다. 이 저장소의 `collected_month` Param 이 이 패턴입니다
- `catchup=False` 는 기본값으로 두고, 과거분은 수동 트리거로 명시적으로 돌립니다.
  `catchup=True` 로 켰다가 수백 개 실행이 동시에 뜨는 사고가 흔합니다
- `max_active_runs=1` 이 없으면 백필과 정기 실행이 같은 파티션을 동시에 씁니다
- 원본(Bronze)은 지우지 않습니다. 재처리는 Bronze 에서 다시 만드는 것이고,
  Bronze 가 덮어써졌으면 복구 경로가 없습니다

## 5. 비용과 규모

수치 근거 없이 "비용이 걱정된다" 고 쓰지 마세요. 계산은 대개 곱셈 한 줄입니다.

- **Lambda**: 최대 실행 15분, 메모리·시간 과금. 크롤링이 15분에 걸릴 가능성이 있으면
  분할 또는 다른 런타임입니다. `execution_timeout` 이 Lambda 한계보다 길면 의미가 없습니다
- **EMR / Spark**: vCPU·메모리 × 시간. 데이터가 수십 GB 미만이면 단일 노드 처리(pandas,
  pyarrow, DuckDB)가 클러스터보다 싸고 빠릅니다. **"Spark 를 쓸 만큼 큰가" 를 먼저 묻는 것이
  시니어의 기본 질문입니다**
- **S3**: 저장보다 요청 수가 먼저 아픕니다. 작은 파일 다수 = LIST/GET 폭증
- 서빙 DB(Postgres)는 스캔량이 아니라 **동시 접속과 인덱스**가 병목입니다. 대시보드용
  집계는 미리 만들어 두고(Gold), 대시보드가 원본을 훑게 하지 않습니다

**판단선**: 규모를 말할 때는 현재 행 수·파일 크기를 실제로 재서 씁니다.
"확장성" 은 숫자 없이는 판정할 수 없는 단어입니다.

## 6. 오케스트레이션 안티패턴

- **task 과분할**: 실패 복구는 빨라지지만 스케줄러 부담과 큐 대기가 늘어납니다.
  이 저장소의 기준(논리 단위로 묶고, 5분 넘는 작업만 분리)이 합리적인 지점입니다
- **센서로 대기**: 폴링 센서는 워커 슬롯을 점유합니다. 데이터 도착을 기다려야 하면
  deferrable/reschedule 모드나 이벤트 기반으로 바꿉니다
- **시간으로 의존 관계 표현**: "A 는 2시, B 는 3시" 는 A 가 늦으면 B 가 빈 데이터를 읽습니다.
  의존은 데이터 존재로 확인해야 합니다
- **XCom 에 데이터 넣기**: XCom 은 메타DB 에 들어갑니다. 경로·행 수 같은 작은 값만.
  DataFrame 을 넘기면 메타DB 가 망가집니다
- **DAG 파일에서 무거운 import·API 호출**: DAG 파싱은 주기적으로 반복됩니다. 파싱 시점에
  네트워크를 타면 스케줄러가 느려집니다
- **retry 가 중복을 만든다**: `retries` 는 멱등성이 보장된 다음에 의미가 있습니다.
  멱등하지 않은 쓰기에 retry 를 붙이면 재시도가 곧 데이터 오염입니다

## 7. 데이터 품질 계층

한 번에 다 하려 들면 아무것도 안 됩니다. 순서가 정해져 있습니다.

1. **계약**: 스키마·타입·필수 컬럼. 어기면 즉시 실패. 가장 싸고 가장 많이 잡습니다
2. **불변식**: 행 수 > 0, 값 범위, 유니크, 파티션당 예상 행수. 어기면 실패
3. **통계**: 분포·전월 대비 변화율. 어기면 **경고**. 실패로 걸면 오탐으로 팀이 알림을 끕니다
4. **참조 정합성**: 조인 키가 다른 테이블에 존재하는지. Silver→Gold 단계에서

**판단선**: 1번이 없는데 3번을 도입하려는 계획은 순서가 거꾸로입니다.
그리고 검증 코드 자체에 테스트가 없으면 계층이 몇 개든 신뢰할 수 없습니다.

## 8. 관측성과 SLA

파이프라인에서 봐야 하는 축은 네 개입니다 — **신선도, 볼륨, 스키마, 분포.**
이 중 신선도가 가장 자주 깨지고 가장 늦게 발견됩니다("어제 데이터가 없어요").

- 실패 알림은 사람에게 도달해야 의미가 있습니다. 알림 경로 자체를 테스트하세요.
  이 저장소에서 `on_failure_callback` 이 import 실패로 조용히 무력화된 적이 있습니다
- 알림에는 **다음 행동**이 들어가야 합니다. "DAG 실패" 만 오면 로그를 뒤지는 시간이 붙습니다
- SLA 는 "몇 시까지 어제 데이터가 있어야 하는가" 로 정의합니다. 이게 없으면
  늦은 것과 안 온 것을 구분할 수 없습니다

## 9. 로컬·운영 동등성

"로컬에서 됐는데 운영에서 안 된다" 의 원인은 거의 항상 **버전과 경로**입니다.

- 버전 핀에는 **근거를 주석으로** 남깁니다. 근거 없는 핀은 다음 사람이 올리고,
  근거 있는 핀은 살아남습니다. 이 저장소의 pyproject 주석이 좋은 예입니다
- 로컬과 운영이 다른 배포판을 쓰면(로컬 `pyspark`, 운영 EMR Spark) 그 차이를 문서에
  적고, 다른 부분에서만 도는 코드를 만들지 않습니다
- 파일 경로 대 객체 스토리지는 Loader 경계에서만 갈리게 합니다. 비즈니스 로직이
  `Path` 를 알면 S3 로 옮길 때 전부 고쳐야 합니다

## 10. 데이터 엔지니어링의 오버엔지니어링 유형

같은 실수가 반복되는 목록입니다. 발견하면 세어서 판정하세요.

- **모든 소스를 위한 제네릭 커넥터**: 소스가 3개인데 플러그인 구조를 만든 경우.
  소스마다 인증·페이지네이션·오류가 달라서 결국 분기로 덮입니다
- **자체 재시도·스케줄·큐**: Airflow 가 이미 합니다. 래퍼는 실패를 두 겹으로 숨깁니다
- **자체 데이터 품질 프레임워크**: 검사 3개를 위해 규칙 엔진을 만드는 경우.
  함수 하나로 시작해서 세 번째 복붙에서 공통화합니다
- **미래 규모용 파티션 과분할**: 하루 수천 행인데 시간 단위 파티션
- **쓰이지 않는 설정 knob**: 호출처가 전부 같은 값을 넘기는 파라미터
- **계층만 늘리는 추상**: 데이터를 그대로 통과시키는 래퍼 클래스
- **결과가 같은 두 경로**: 같은 변환을 Spark 와 pandas 양쪽에 구현. 둘이 어긋나기 시작합니다

반대로 **과잉이라고 잘못 판정하기 쉬운 것들**: 런타임 경계를 넘는 계약(`pipeline_core`),
근거 있는 버전 핀, 재실행 안전성을 위한 코드, 검증 task. 이것들은 지금 필요한 것입니다.

## 11. 도구를 도입할 시점

**규칙 셋(rule of three)**: 같은 문제를 손으로 세 번 고쳤을 때 도구를 봅니다.
두 번째까지는 복붙이 더 싸고, 네 번째부터는 복붙이 비쌉니다.

도입 판단에는 실측이 필요합니다.

- 의존성 비용: `uv add` 를 사본에서 돌려 **패키지 증가 수와 기존 버전 변경**을 셉니다.
  기존 핀을 내리게 만드는 도구는 그 핀이 왜 있는지 확인한 뒤에 결정합니다
- 학습 비용: 팀에서 그 도구를 아는 사람이 몇 명인지. 아무도 모르면 도입 후 방치됩니다
- 이탈 비용: 나중에 걷어낼 수 있는지. 설정이 코드 밖(YAML·SaaS)에 쌓이는 도구는 이탈이 비쌉니다
- **팀원이 설치하지 않으면 없는 것과 같습니다.** 저장소에 들어가 자동으로 도는 것(git 추적
  파일, 훅)과 각자 깔아야 하는 것(플러그인, 로컬 CLI)을 구분해서 판단하세요
