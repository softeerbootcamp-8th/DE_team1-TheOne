# 엔지니어링 평가

리뷰가 쓸모없어지는 방식은 정해져 있습니다. **근거 없는 인상 비평**("복잡해 보인다",
"확장성이 부족하다")과 **모든 것을 지적하는 목록**입니다. 전자는 반박할 수 없어서 무시되고,
후자는 우선순위가 없어서 무시됩니다.

그래서 이 스킬의 규칙은 두 개입니다.

1. **판정 하나 = 실행한 명령 하나 + 그 출력.** 세지 않고 "많다"고 쓰지 않습니다.
2. **조용히 틀린 값을 먼저 잡는다.** 실패로 드러나는 버그는 누구나 발견하지만,
   성공으로 끝나면서 틀린 숫자를 만드는 코드는 분기 마감에 발견됩니다.

## 0. 호출 경로를 먼저 확인한다

같은 스킬이지만 두 경로는 다르게 행동해야 합니다.

| 경로 | 범위 | 보고 개수 | 태도 |
|---|---|---|---|
| **훅 자동 호출** (커밋 전·PR 전) | staged diff 또는 `origin/develop...HEAD` | **최대 3건** | 이번 변경이 만든 것만. 원래 있던 문제는 언급하지 않음 |
| **사용자 직접 호출** | 지정한 경로·질문 범위 | 제한 없음 | 전면 평가, 개선안까지 |

훅 경로에서 15건을 쏟아내면 팀원은 훅을 끕니다. **끄면 이 스킬의 가치는 0입니다.**
이번 diff 가 만든 문제가 없으면 "차단 사유 없음" 한 줄로 끝내는 것이 정답입니다.

훅에서 호출된 경우, 검토를 마치면 통과를 기록해야 커밋·PR 이 진행됩니다.

```bash
python3 .claude/hooks/review_gate.py --pass commit   # 또는 --pass pr
```

이건 "문제가 없다" 는 도장이 아니라 **"사람이 볼 수 있게 판정을 남겼다"** 는 기록입니다.
3분류 결과를 사용자에게 보여주지 않은 채 이걸 실행하면 훅이 있는 이유가 사라집니다.

## 1. 사실을 모은다 (추측 금지)

```bash
git diff --cached --stat          # 훅: 커밋 전
git diff origin/develop...HEAD --stat   # 훅: PR 전
```

저장소에 없는 파일·함수를 언급하면 리뷰 전체의 신뢰가 무너집니다. 인용 전에 확인합니다.

```bash
rg -n "<함수명>" --type py -g '!**/.venv/**'   # 실제 호출처 세기
```

**이 프로젝트의 고정 사실** — 평가의 기준선입니다. 여기에 어긋나는 제안은 하지 않습니다.

- 메달리온: Bronze 는 원본만(`Extract → Load`), 정제·집계는 Silver·Gold (`docs/PIPELINE_CORE.md`)
- 런타임 3개는 **일부러** 분리: pandas 가 airflow 2.1.4 / spark 3.0.1 로 다름. `libs/pipeline_core`
  는 `abc`·`typing`·`dataclasses` 만 씁니다 — 여기에 의존성을 추가하면 분리 자체가 무너집니다
- spark 의 numpy·pandas·pyarrow 핀은 EMR 7.13 이 제공하는 값과 **일치시킨 것**입니다.
  "최신으로 올리자" 는 제안은 EMR 런타임을 덮어써서 로컬 통과·운영 실패를 만듭니다
- lambda 의 pillow·pyarrow 상한은 베이스 이미지 glibc 2.26 이 정합니다
- **로컬 실행(`docker compose up`)은 깨면 안 되는 제약입니다.** 클라우드 이관 제안도
  로컬 경로를 남기는 형태여야 채택 가능합니다
- 과거 결정은 `docs/decision_making/<날짜>.md` 에 있습니다. 충돌하는 제안을 하려면
  그 날짜와 항목 번호를 인용하고 무엇이 달라졌는지 적습니다

## 2. 세 가지로 분류한다

판정은 **과잉 / 부족 / 적정** 세 개뿐입니다. "적정"을 빼먹지 마세요 —
잘한 결정을 확인해 주지 않는 리뷰는 팀이 왜 그렇게 했는지를 잊게 만듭니다.

### 과잉 (over-engineering)

지금 필요 없는 것을 지금 만든 경우입니다. 판정은 **세어서** 합니다.

| 의심 | 확인 명령 | 과잉 판정선 |
|---|---|---|
| 추상 클래스·인터페이스 | `rg -n "class \w+\(<추상명>\)"` | 구현체 1개 |
| 설정 knob·파라미터 | `rg -n "<파라미터명>"` | 호출처 전부 같은 값 |
| 헬퍼·유틸 | 표준 라이브러리·기존 모듈에 같은 것이 있는지 | 이미 있음 |
| 계층 추가 | 그 계층을 지나가는 데이터가 바뀌는지 | 그대로 통과 |

주의 — **구현체 1개라고 항상 과잉은 아닙니다.** `libs/pipeline_core` 처럼 런타임 경계를
넘는 계약이면 구현체가 하나여도 그게 존재 이유입니다. 세고 나서 "이 추상이 없으면 무엇이
불가능해지나" 를 한 줄로 답할 수 있는지 보세요. 답이 없으면 과잉입니다.

### 부족 (under-engineering)

돌아가지만 **조용히 틀릴 수 있는** 상태입니다. 이 프로젝트에서 반복 발생한 실제 유형:

- **재실행이 값을 바꾼다.** 같은 입력을 두 번 처리했을 때 행이 늘어나는지. `retries: 1` 이
  있으므로 재시도 한 번으로 재현되는 종류입니다
- **파티션 키가 데이터의 자연 키와 다르다.** 수집일로 파티션하고 월 단위 데이터를 담으면
  재수집분이 합산됩니다
- **적재 후 아무도 확인하지 않는다.** 0행·스키마 변경이 성공으로 끝나는 DAG
- **검증 로직에 테스트가 없다.** 검증이 틀리면 검증이 없는 것보다 나쁩니다(있다고 믿게 됨)
- **알림이 죽어 있다.** `on_failure_callback` 이 import 실패로 무력화된 적이 있습니다
- **로컬과 운영이 다른 코드로 돈다.** 로컬 pyspark 와 EMR Spark, 로컬 파일과 S3

각 항목의 확인 질문은 하나입니다 — **"이게 틀렸을 때 누가, 얼마나 뒤에 알게 되나."**
사람이 눈으로 숫자를 볼 때 알게 되는 구조면 부족입니다.

### 적정

지금 규모에 맞는 선택입니다. 근거를 한 줄로 남기면 나중에 누가 "이거 왜 이래요" 라고
물을 때 이 리뷰가 답이 됩니다.

## 3. 우선순위를 매긴다

심각도는 **발견 시점**으로 정합니다. 이 순서를 바꾸지 마세요.

1. **조용히 틀린 값** — 성공으로 끝나고 숫자가 틀림. 즉시
2. **드러나는 실패** — DAG 가 빨갛게 죽음. 다음 스프린트
3. **운영 부담** — 사람이 매번 손을 대야 함. 백로그
4. **유지보수** — 지금 아프지 않음. 이슈만 남김

"과잉" 은 대개 3~4번입니다. 오버엔지니어링을 1번으로 올려 리팩터링을 우선하게 만드는
리뷰는 팀의 시간을 잘못 쓰게 합니다 — 지저분한 코드보다 조용히 틀린 값이 비쌉니다.

## 4. 보고 형식

훅 경로에서는 이 표만, 사용자 직접 호출에서는 표 + 개선안을 씁니다.

```markdown
## 판정

| 분류 | 대상 | 근거 | 심각도 |
|---|---|---|---|
| 부족 | `airflow/dags/x_dag.py:88` 적재 후 검증 없음 | `rg -c "validate" 결과 0` | 1 |
| 적정 | 런타임별 uv.lock 분리 유지 | pandas 2.1.4 vs 3.0.1 실측 충돌 | – |
| 과잉 | `common/retry.py` 재시도 래퍼 | 호출처 1곳, Airflow `retries` 와 중복 | 3 |

## 근거

<명령과 출력. 세지 않은 주장은 쓰지 않는다>

## 개선안 (사용자 호출 시에만)

<가장 싼 수정 1개. 이슈로 낼 만하면 초안까지>
```

판정이 없으면 **"이번 변경에서 차단 사유 없음"** 이라고 쓰고 끝냅니다.
억지로 찾아낸 지적 한 건이 리뷰 전체의 신뢰를 깎습니다.

## 5. 의사결정 상담

"A 로 갈까요 B 로 갈까요" 를 물어오면, 답보다 먼저 **되돌릴 수 있는 결정인지** 가릅니다.

- **되돌릴 수 있음**(코드 구조, 라이브러리 선택) → 빠르게 정하고 넘어갑니다. 여기서
  비교표를 세 장 만드는 게 시간 낭비입니다
- **되돌리기 어려움**(저장 레이아웃, 파티션 키, 스키마, 과금 구조) → 근거를 **실측**으로
  만듭니다. 의존성 비용은 `uv` 로 해석해 패키지 증가 수를 세고, 성능은 작은 샘플로 재고,
  비용은 단가 × 예상량으로 계산합니다. 추정치는 추정치라고 적습니다

결정이 끝나면 `docs/decision_making/<오늘날짜>.md` 에 결론과 **기각한 대안, 기각 이유**를
남기라고 권하세요. 결론만 남은 문서는 반년 뒤에 같은 논쟁을 다시 시작하게 만듭니다.

깊은 판단이 필요할 때(비용 추정, 규모 한계, 스키마 진화, 백필 전략, 오케스트레이션
안티패턴)는 `references/senior-de-playbook.md` 를 읽으세요. 이 파일에 유형별 실패 사례와
판단선이 들어 있습니다.

## 6. 이 스킬이 하지 않는 것

- **버그 사냥이 아닙니다.** 로직 오류·예외 처리는 테스트와 코드 리뷰의 몫입니다.
  여기서 보는 건 "구조가 이 문제를 다시 만들 수 있는가" 입니다
- **스타일 지적을 하지 않습니다.** 네이밍·포매팅은 판정 대상이 아닙니다
- **다시 쓰라고 하지 않습니다.** 개선안은 항상 **가장 싼 수정**부터. 전면 재작성은
  그것 말고 답이 없을 때만, 그리고 왜 없는지를 적어서
