# 작업 시작

팀 규칙(`README.md`)은 모든 작업이 **이슈 → 브랜치 → 커밋 → PR** 을 거치게 되어 있습니다.
각 단계를 어떻게 쓰는지는 이미 네 개의 스킬에 적혀 있습니다. 그런데 실제로 빠지는 건
개별 단계의 품질이 아니라 **순서와 인수인계** 입니다. 이슈를 만들고 번호를 잊어서
브랜치 이름이 규칙과 어긋나거나, 구현부터 하고 나중에 이슈를 소급 발행하거나,
`develop` 에서 작업하다 커밋 직전에 알아차리는 식입니다.

이 스킬은 그 이어붙이는 일만 합니다. **각 단계의 작성 규칙을 여기 다시 쓰지 마세요** —
해당 스킬이 유일한 기준이고, 팀이 그쪽을 고치면 이 스킬은 자동으로 따라가야 합니다.

## 0. 지금 어느 단계인가

이 스킬은 두 국면으로 나뉩니다. **브랜치 이름이 어느 국면인지 알려 줍니다.**

```bash
git branch --show-current
git status --short
```

| 현재 브랜치 | 국면 | 할 일 |
|---|---|---|
| `main` / `develop` | **착수** | 1 → 2 → 3 을 하고 사용자에게 넘김 |
| `<type>/<번호>-<슬러그>` | **마무리** | 4 → 5 → 6 |

애매하면 (번호 없는 브랜치, 예상 밖 이름) 추측하지 말고 사용자에게 물어보세요.
잘못 판단하면 이미 있는 작업에 새 이슈를 얹거나, 착수해야 할 때 커밋을 시도합니다.

# 착수 국면

## 1. 무엇을 할지 확정한다

여기가 이 스킬 고유의 일입니다. 이슈를 쓰려면 네 가지가 정해져 있어야 하고,
정해지지 않은 채로 이슈를 쓰면 그 이슈는 리뷰어에게 아무것도 알려 주지 못합니다.

| 정할 것 | 왜 지금 정하나 |
|---|---|
| **무엇이 문제/필요인가** (한 문장) | 이슈의 "작업 목적" 이 됩니다 |
| **손댈 파일·영역** | 이슈 본문의 근거이자, 범위가 하나인지 판단하는 재료 |
| **완료를 어떻게 판정하나** | 이슈의 "완료 조건". 돌려볼 명령으로 씁니다 |
| **타입** (`feat`/`fix`/`refactor`/`docs`/`test`/`chore`) | 이슈 템플릿·라벨, 브랜치 접두사, 커밋 `type` 이 전부 여기서 갈립니다 |

사용자 말만으로 부족하면 **직접 코드를 읽어 확인하세요.** 손댈 파일을 추측으로 적으면
이슈·브랜치 이름·PR 이 전부 그 추측 위에 쌓입니다. 확인이 싼 단계에서 확인하는 게
이 순서의 목적입니다.

### 범위가 하나의 이슈로 안 끝날 것 같으면 멈춘다

작업 도중이 아니라 **여기서** 판단하는 게 가장 쌉니다. 아래 신호가 보이면 진행을 멈추고
사용자에게 쪼갤지 물어보세요. **이슈를 임의로 여러 개 발행하지 마세요** — 티켓을 만드는
건 사람의 결정이고, 원치 않는 티켓이 늘어나면 보드가 신뢰를 잃습니다.

- 변경이 300줄을 넘을 것 같다 (팀 이슈/PR 크기 기준)
- 원인이 다른 문제가 섞여 있다 — 되돌릴 단위가 다르면 이슈도 다릅니다
- **의존성 버전 변경과 기능 변경이 같이 있다** — `README.md` 규칙 7 이 분리된 PR 을
  요구합니다 (`pyproject.toml` 과 `uv.lock` 은 함께, 기능과는 따로)
- 선행 결정이 안 난 항목에 걸려 있다 (`docs/decision_making/` 의 미결 항목)

쪼개기로 하면 **지금 착수할 것 하나만** 이슈로 만들고, 나머지는 이슈 본문의
"참고 자료 / 관련 이슈" 에 후속으로 적습니다.

## 2. 이슈를 확인하고, 없으면 발행한다

### 먼저 이미 있는 이슈를 찾는다

**새로 만들기 전에 열린 이슈 목록을 봅니다.** 팀원이 이미 올렸거나, 사용자가 며칠 전에
만들어 두고 잊었을 수 있습니다. 중복 이슈는 번호가 두 개로 갈려서 브랜치·PR·`Closes #`
가 서로 다른 티켓을 가리키게 되고, 보드에서 같은 일이 두 줄로 남습니다.

```bash
gh issue list --state open --limit 50
gh issue list --state open --search "<핵심 키워드>"    # 예: "파티션", "logging", "스킬"
```

닫힌 이슈도 한 번 보세요 — 같은 문제가 이미 처리됐다면 지금 하려는 게 회귀일 수 있습니다.

```bash
gh issue list --state closed --search "<핵심 키워드>" --limit 20
```

**찾은 이슈가 지금 하려는 일과 같으면 그 번호를 씁니다.** 새로 만들지 마세요. 다만
"같다" 를 넉넉하게 판정하지 마세요 — 제목이 비슷해도 범위가 다르면 다른 이슈입니다.
애매하면 후보를 보여주고 사용자에게 물어보세요.

| 상황 | 할 일 |
|---|---|
| 같은 일의 이슈가 있다 | 그 번호를 3단계로 넘김. 발행 생략 |
| 비슷하지만 범위가 다르다 | 후보를 제시하고 사용자 판단을 받음 |
| 관련은 있으나 별개다 | 새로 발행하고, 본문 "참고 자료 / 관련 이슈" 에 그 번호를 적음 |
| 없다 | 새로 발행 |

### 없으면 발행한다

`write-issue` 스킬로 진행합니다. 1단계에서 확정한 네 가지를 그대로 넘기세요.

**어느 쪽이든 이슈 번호를 반드시 확보해야 합니다.** 번호가 없으면 브랜치 이름
규칙(`<type>/<번호>-<작업명>`)도 PR 의 `Closes #` 도 지킬 수 없습니다. `gh` 인증이 안 되어
있어 조회·등록이 막히면 거기서 멈추고 사용자에게 알리세요 — 번호 없이 브랜치를 만들고
나중에 이름을 고치는 것보다 낫습니다.

## 3. 브랜치를 만든다

**먼저 이미 있는지 확인합니다.** 사용자가 이슈를 만들 때 브랜치도 같이 만들어 뒀을 수
있습니다. 있는 걸 두고 새로 만들면 작업이 두 갈래로 갈라집니다.

```bash
git branch -a | grep -i "<이슈번호>"
```

있으면 그걸 씁니다 (`git switch <그 브랜치>`). 없으면 만듭니다.

```bash
git switch -c <type>/<이슈번호>-<작업명> develop
```

이름의 세 조각은 **전부 이미 정해진 값에서 가져옵니다.** 새로 지어내는 부분이 없어야
브랜치·이슈·커밋·PR 이 같은 번호를 가리킵니다.

| 조각 | 어디서 오나 | 예 |
|---|---|---|
| `<type>` | 1단계에서 정한 타입 (`feature` `fix` `refactor` `docs` `test` `chore` `hotfix`) | `fix` |
| `<이슈번호>` | 2단계에서 확보한 번호 (찾은 이슈든 새로 만든 이슈든) | `173` |
| `<작업명>` | **그 이슈의 제목**에서 뽑은 슬러그 | `hvfhv-bronze-year-month-partition` |

`<작업명>` 은 이슈 제목을 영문 소문자·하이픈으로 옮긴 것입니다. 사용자 말이나 내 요약이
아니라 **이슈 제목**이 출처입니다 — 그래야 나중에 브랜치 목록만 보고 어느 티켓인지
알 수 있습니다.

```
[Fix] hvfhv Bronze 가 수집일로 파티션돼 재수집분이 중복 집계됨
  → fix/173-hvfhv-bronze-partition-key
```

- **base 는 항상 `develop`** — `main` 이 아닙니다 (`README.md` Branch Rule)
- 소문자, 공백 대신 `-`, 3~5 단어로 줄입니다. 제목을 그대로 음차하지 마세요
- 브랜치 이름은 위 세 값에서 **결정되는 값**이라 따로 승인받지 않습니다.
  다만 이미 있는 브랜치를 무시하고 새로 파는 건 승인 없이 하면 안 됩니다

**커밋 footer 와 PR 의 `Closes #` 는 이 번호를 그대로 씁니다.** `write-commit` 과
`write-pr` 이 브랜치 이름에서 번호를 꺼내므로, 브랜치 이름이 맞으면 나머지는 따라옵니다.
반대로 브랜치 번호가 틀리면 세 곳이 같이 틀립니다.

미커밋 변경이 있으면 브랜치를 옮겨도 그대로 따라옵니다. 다만 **이 작업과 무관한 변경이
섞여 있으면 사용자에게 알리세요** — 나중에 `git add` 할 때 같이 딸려 들어갑니다.

## 여기서 사용자에게 넘긴다

구현은 대화가 길고 방향이 바뀌기 마련이라 스킬이 붙들고 있기에 맞지 않습니다.
판을 깔았다는 것과 다음에 무엇을 하면 되는지를 알려 주고 빠집니다.

```
이슈 #<번호> 등록, 브랜치 <이름> 생성했습니다.

작업: <한 문장>
완료 판정: <돌려볼 명령>

구현이 끝나면 "마무리해줘" 라고 하시면 테스트 → 커밋 → PR 로 이어서 진행합니다.
```

# 마무리 국면

작업 브랜치에서 이 스킬이 다시 불렸을 때입니다. 구현이 끝났다고 보고 정리합니다.

## 4. 테스트

`write-test` 스킬로 진행합니다. 그 스킬이 시나리오 표를 뽑아 사용자 승인을 받고 씁니다.

문서·설정만 바뀌어서 테스트가 의미 없는 경우에는 건너뛰되, **건너뛴다는 사실과 사유를
사용자에게 한 줄로 알리세요** (예: "문서 변경만이라 테스트 생략"). 조용히 건너뛰면
"테스트 없이 넘어가기" 가 기본값이 됩니다. 판단이 애매하면 건너뛰지 말고 물어보세요.

## 5. 커밋

`write-commit` 스킬로 진행합니다. 기능 단위로 나누되, 나누는 기준은 하나입니다 —
**각 커밋에서 테스트가 통과해야 합니다.**

그래서 구현과 그 구현을 검증하는 테스트는 **같은 커밋**에 넣습니다. 나누면 중간 커밋이
빨간불이 되어 `git bisect` 나 CI 가 무관한 실패를 짚습니다. 반대로 성격이 다른 변경
(기능 + 빌드 설정, 기능 + 문서)은 나눕니다 — 되돌릴 단위가 다릅니다.

`git add .` 을 쓰지 마세요. 3단계에서 확인한 "무관한 변경" 이 그대로 딸려 들어갑니다.
경로를 명시해서 스테이징합니다.

> 이 스킬을 호출한 것이 커밋 권한입니다. 사용자가 이 흐름을 시작했다는 것 자체가
> 커밋까지의 동의이므로, 커밋 직전에 다시 확인받지 않습니다. 대신 커밋 후 무엇을
> 어떻게 나눴는지 보고하세요.

## 6. PR

`write-pr` 스킬로 진행합니다. 브랜치 이름의 번호가 `Closes #<번호>` 로 들어갑니다
(그 스킬이 브랜치 이름에서 꺼내니 따로 넘길 것은 없습니다).

PR 은 팀 전체가 보는 산출물이라 `write-pr` 이 등록 전 승인을 받습니다. 그 게이트를
건너뛰지 마세요.

## 이 흐름에서 지키는 것

개별 스킬에 적혀 있지 않거나, 여러 단계에 걸쳐 있어서 놓치기 쉬운 것들입니다.

- **`develop` / `main` 에서 구현하지 않습니다.** 두 브랜치는 직접 커밋·푸시 금지이고
  PR 로만 병합됩니다. 0단계에서 걸러지지만, 마무리 국면에 들어와서 브랜치가 `develop`
  이면 커밋하지 말고 멈추세요.
- **브랜치는 이슈 번호가 나온 뒤에만 만듭니다.** 그리고 만들기 전에 이미 있는지 봅니다.
- **이슈는 늘리지 않습니다.** 만들기 전에 `gh issue list` 로 같은 일의 이슈가 이미
  있는지 봅니다(2단계). 범위가 커지면 사용자에게 묻습니다.
- **네 산출물이 같은 번호를 가리켜야 합니다.** 이슈 / 브랜치 이름 / 커밋 footer /
  PR `Closes #`. 마무리 국면에 들어왔을 때 브랜치 번호가 실제 이슈와 맞는지 한 번
  확인하세요 — 번호가 틀린 브랜치에서 커밋하면 PR 이 남의 티켓을 닫습니다.

  ```bash
  gh issue view "$(git branch --show-current | sed -E 's|.*/([0-9]+)-.*|\1|')" --json number,title,state
  ```
- **로컬 실행을 깨지 않습니다.** 이 저장소는 `docker-compose` 로컬 파이프라인에서
  검증합니다. 클라우드 전환을 앞당기는 변경이라도 로컬 실행 경로가 살아 있어야 하고,
  못 살리면 그 사실을 먼저 알리고 사용자 판단을 받으세요.
- **확인한 것만 씁니다.** 이슈·커밋·PR 에 들어가는 경로·명령·수치는 실제로 돌려보고
  얻은 것이어야 합니다. 세 산출물이 같은 추측을 반복하면 틀렸을 때 셋 다 고쳐야 합니다.

## 중간에 멈췄을 때

흐름이 끊기는 건 정상입니다 (이슈만 만들고 하루 지남, 구현 중 다른 일이 끼어듦).
다시 불렸을 때는 0단계로 돌아가 브랜치를 보고 이어서 하면 됩니다. 앞 단계를 다시
하지 마세요 — 이슈가 이미 있는데 또 만드는 것이 이 흐름에서 가장 흔한 사고입니다.

이미 커밋이 있는 브랜치에서 불렸다면 4~6 중 남은 것만 합니다.

```bash
git log --oneline develop..HEAD    # 커밋이 있으면 5단계는 일부 끝난 것
gh pr list --head "$(git branch --show-current)"   # PR 이 이미 있으면 6단계 끝
```
