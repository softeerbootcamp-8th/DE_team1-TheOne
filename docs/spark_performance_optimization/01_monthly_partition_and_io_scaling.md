# 필요한 월과 지역만 처리하는 파티션 설계

- 요약
  - 데이터가 매달 쌓이고 같은 달의 원본이 다시 수집되면, 전체 경로를 읽는 방식은 처리량이 계속 늘고 중복된 버전을 함께 읽을 수 있음
  - 읽기 범위를 운영 지역과 월로 제한하고, 각 월에서는 처리가 끝난 최신 수집본 하나만 선택
  - 정제 데이터는 월별로 저장하고 변경된 월만 다시 쓰도록 수정해, 2024년 3월 재처리 때 2월 데이터가 삭제되던 회귀를 차단
  - 다음 단계의 입력 식별은 파일을 1MiB씩 읽어 SHA-256을 계산하므로 수백 MB 파일도 한 번에 메모리에 올리지 않음

## 문제

월간 운행 원본은 시간이 지날수록 계속 늘어난다. 모든 기간을 한 경로에 두고 매번 전체를 읽으면, 한 달을 다시 처리할 때도 과거 데이터까지 읽게 된다.

같은 달의 원본이 여러 번 수집될 수도 있다. 이때 수집 버전을 구분하지 않고 월 디렉터리 전체를 읽으면 이전 파일과 최신 파일이 함께 들어간다. 같은 운행 기록을 중복 처리할 가능성이 생긴다.

운영 지역이 늘어날 때도 같은 문제가 생긴다. 지역 경계가 경로에 없으면 한 지역을 처리하는 작업이 다른 지역의 파일까지 탐색하거나 읽을 수 있다.

쓰기 단계에서는 실제 데이터 삭제 문제가 있었다. 정제된 데이터(Silver)를 기본 `overwrite` 모드로 저장했더니, 2024년 3월을 다시 적재할 때 같은 저장 경로에 있던 2월 파티션까지 삭제됐다. 한 달의 재처리가 다른 달의 데이터를 바꾼 것이다.

입력이 같은지를 경로만으로 판단하는 방식도 부족했다. 같은 경로에 다른 내용이 다시 발행되면 변경을 알아낼 수 없다. 반대로 파일 내용을 확인하려고 수백 MB의 Parquet 파일을 한 번에 읽으면 드라이버 메모리에 부담을 줄 수 있다.

## 접근

읽기, 쓰기, 입력 식별에 같은 데이터 경계를 사용했다.

저장 경로는 `운영 지역 → 대상 월 → 수집 버전` 순서로 나눴다. 작업은 먼저 운영 지역과 월을 정한 뒤, 그 범위 안에서 완료 표시가 있는 최신 수집본 하나만 고른다. 수집 중인 파일이나 이전 수집본은 처리 대상에서 제외한다.

재처리 범위는 시작 월과 종료 월로 받는다. 전체 이력을 고정적으로 읽지 않고 한 달 또는 필요한 월 구간만 선택할 수 있다. 구간 안에 원본이 없는 월이 있으면 Spark 계산을 시작하기 전에 누락된 월을 모아 실패하도록 했다. 일부 월만 처리된 상태가 남는 것을 피하기 위한 선택이다.

쓰기에서는 전체 디렉터리 덮어쓰기와 월 파티션 덮어쓰기를 구분했다. 월 파티션으로 저장할 때만 Spark의 동적 파티션 덮어쓰기를 사용한다.

입력 변경 여부는 경로 대신 파일 이름과 실제 바이트로 판단했다. 단, 파일 전체를 메모리에 올리지 않고 일정한 크기의 청크로 나눠 읽도록 했다.

## 해결

수집한 원본 데이터(Bronze)는 운영 지역과 `year_month=YYYY-MM` 경로 아래에 저장한다. 각 월에는 수집 시각이 다른 버전이 여러 개 있을 수 있다. 읽기 로직은 완료 표시가 있는 버전만 비교하고, 수집 시각이 가장 늦은 Parquet 파일 하나를 반환한다. 로컬 파일과 S3에 같은 선택 규칙을 적용했다.

시작 월과 종료 월을 지정하면 양끝을 포함한 월 목록을 만든다. 예를 들어 2023년 11월부터 2024년 2월까지 요청하면 다음 네 파티션만 읽는다.

```text
운영 지역/2023-11의 최신 완료본
운영 지역/2023-12의 최신 완료본
운영 지역/2024-01의 최신 완료본
운영 지역/2024-02의 최신 완료본
```

정기 실행은 한 지역의 한 달 버전을 해당 월 경로에 기록한다. 여러 달을 다시 적재할 때는 정제 결과를 `year_month`로 나누고 `partitionOverwriteMode=dynamic`을 사용한다. 이 설정은 이번 실행에 포함된 월만 교체한다. 다른 월의 파일은 그대로 둔다.

파티션 값은 파일 본문에서 제외한다. Spark가 `year_month=YYYY-MM` 경로에서 월 값을 복원하므로, 같은 값을 모든 행에 반복해서 저장하지 않는다. 저장 전에 나머지 컬럼의 이름과 자료형이 예상한 물리 스키마와 같은지도 확인한다.

다음 처리 단계는 입력 파일의 이름과 내용을 정렬된 순서로 이어 SHA-256을 계산한다. 파일 내용은 1MiB씩 읽는다. 파일 추가, 삭제, 이름 변경, 내용 변경 중 하나라도 있으면 해시가 달라진다. S3 객체를 찾을 때는 경로 끝에 `/`를 붙여, 이름이 비슷한 다른 디렉터리까지 함께 해시하지 않도록 했다.

## 검증

실행 시간이나 스캔 바이트의 적용 전후 수치는 측정하지 않았다. 따라서 비용이나 처리 시간 감소를 결과로 주장하지 않는다. 검증은 읽고 쓰는 범위와 메모리 사용 방식이 코드의 의도대로 동작하는지에 집중했다.

- 월 범위 테스트에서 단일 월, 여러 월, 연도를 넘는 구간이 모두 양끝을 포함해 선택되는지 확인했다.
- 두 달을 입력한 통합 테스트에서 결과에 두 월만 저장되는지 확인했다.
- 요청 구간에 원본이 없는 월이 여러 개 있으면, 첫 번째 누락에서 멈추지 않고 누락 월 전체를 오류에 표시하는지 확인했다.
- 로컬 파일과 모의 S3 환경에서 같은 월의 여러 수집본 중 완료된 최신 파일 하나만 선택하는지 확인했다.
- 운영 지역 경로 생성 테스트에서 다른 지역을 읽기 후보에 포함하지 않는지 확인했다.
- 2월 파티션을 쓴 뒤 3월 파티션을 추가하는 회귀 테스트에서 두 파티션이 모두 남는지 확인했다. 작업 오케스트레이션에서도 쓰기 전후의 월 목록을 비교해, 현재 처리 중인 월을 제외한 기존 월이 사라지면 실패하도록 했다.
- 해시 테스트에서 같은 입력은 같은 64자리 값을 만들고, 파일 내용 변경과 파일 추가·삭제는 다른 값을 만드는지 확인했다.
- 모의 S3 테스트에서 `version/`을 해시할 때 이름이 비슷한 `version_old/`의 객체가 섞이지 않는지 확인했다.

## 결론

한 번의 실행이 읽고 바꾸는 범위를 운영 지역과 월로 제한했다. 같은 달에 원본이 여러 번 들어와도 완료된 최신본 하나만 처리한다. 한 달을 다시 적재해도 다른 달은 남는다.

1MiB 청크 해시는 파일 전체를 메모리에 올리는 문제를 피하지만, 입력 바이트 전체를 읽는 작업 자체는 남는다. 월별 파일 수가 크게 늘거나 작은 파일이 많아지면 객체 목록 조회와 해시 시간이 길어질 수 있다. 그 시점에는 파일 병합이나 검증된 manifest 사용을 다시 검토해야 한다.
