# 무거운 계산의 실패 비용과 중복 적재 줄이기

- 요약
  - 추천 계산이나 두 번째 결과 변환에서 실패하면 계산 시간을 낭비하고, 먼저 쓴 결과만 새 값으로 남을 수 있었음
  - 가벼운 검사를 추천 전에 실행하고 모든 메모리 변환이 끝난 뒤 결과 두 개를 함께 교체
  - PostgreSQL은 세 데이터를 한 트랜잭션으로 쓰고 커밋 전에 행 수를 다시 확인
  - 입력 내용·추천 설정·계산 상수의 SHA-256이 같으면 성공한 기존 버전을 재사용하고 다시 적재하지 않음

## 문제

차량 추천은 기사×차량 후보와 여러 순위 라운드를 계산한다. 기사별 집계가 이미 틀렸는데 추천까지 끝낸 뒤 발견하면 그 계산이 모두 헛일이 된다.

로컬 결과는 기사별 한 달 실적과 기사별 추천 차량 두 파일이다. 이전에는 `toPandas()`와 최종 CSV 쓰기를 한 파일씩 번갈아 실행했다. 두 번째 결과에서 메모리 부족이 나면 첫 파일은 새 값이고 두 번째 파일은 이전 값인 상태가 남을 수 있었다.

운영 데이터베이스에서는 성공한 적재의 응답만 유실될 수 있다. 작업이 실패한 것으로 판단해 다시 실행하면 같은 데이터를 새 버전으로 한 번 더 넣을 수 있다. 경로만 비교하면 같은 경로에 다른 내용이 다시 발행된 경우와 완전히 같은 재시도를 구분할 수도 없다.

## 접근

작업 순서를 `검사 → 무거운 계산 → 메모리 변환 → 임시 저장 → 공개`로 나눴다. 실패할 가능성이 있는 작업을 최종 경로 변경보다 앞에 모았다.

재실행 판단에는 경로 하나가 아니라 결과에 영향을 주는 입력을 모두 넣었다. 같은 실행인지 판단하는 값과 적재 이력을 데이터베이스에 함께 기록했다.

## 해결

기사별 월 집계를 만든 직후 원본 운행의 주행거리와 수익 합계를 대조한다. 이 검사가 통과한 뒤에만 차량 추천 후보와 재고 배정 라운드를 계산한다. 재고 목록이 비어 있으면 N×M 후보를 만들기 전에 중단한다.

로컬 출력은 두 DataFrame의 `toPandas()`를 먼저 모두 끝낸다. 그 다음 각 결과를 최종 파일과 같은 디렉터리의 임시 파일에 쓴다. 두 임시 파일 작성이 모두 끝나야 최종 이름으로 교체한다. 중간에 실패하면 임시 파일을 삭제하고 이전 최종 파일은 건드리지 않는다.

운영 적재는 기사별 실적, 기사별 추천, 실행 계보 세 데이터를 하나의 PostgreSQL 트랜잭션으로 쓴다. 각 테이블을 쓴 뒤 지역·월·버전 조건으로 실제 행 수를 다시 센다. 세 결과가 모두 기대 행 수와 같을 때만 성공 버전 메타데이터를 기록하고 커밋한다.

재실행 식별값에는 다음 항목을 정렬해 넣고 SHA-256을 계산한다.

- 운영 지역과 대상 월
- 정제 입력 네 종류의 경로
- 각 입력 파일의 실제 내용 해시
- 추천 알고리즘 버전과 임계값 목록
- 연료 환산값, 프리미엄 전환 비율, 거리 구간 같은 계산 상수

같은 지역과 월에 같은 식별값이 이미 있으면 기존 버전의 행 수를 확인하고 그 버전을 반환한다. 새 행은 넣지 않는다. 입력 내용이나 추천 설정이 바뀌면 새 식별값과 새 버전을 만든다.

같은 지역·월을 동시에 적재하는 두 실행이 같은 다음 버전을 선택하지 않도록 트랜잭션 잠금을 건다. 다른 지역이나 다른 월은 서로 다른 잠금 키를 사용한다.

작업 중 저장한 Spark DataFrame은 `finally`에서 해제한다. 오류 메시지에 실제 데이터 행을 넣는 `collect()`는 최대 5행으로 제한한다. 알고리즘·임계값의 고유 조합은 작은 설정 목록이라 별도로 가져온다. 전체 결과를 드라이버로 옮기는 작업은 최종 `toPandas()` 두 곳에 모았다.

## 검증

두 번째 CSV 작성에서 `MemoryError`를 발생시키는 테스트를 만들었다. 실패 뒤 두 최종 파일 모두 이전 실행 값을 유지하는지 확인했다. 디스크 오류가 나도 `.tmp` 파일이 남지 않는지도 확인했다.

PostgreSQL 적재 테스트에서는 실제 행 수가 기대보다 적거나 많으면 커밋 전에 실패하는지 확인했다. 성공 버전 메타데이터가 모든 데이터 삽입과 행 수 검사 뒤에 기록되는지도 검사했다.

성공 응답만 유실된 상황은 같은 작업을 연속 두 번 호출해 재현했다. 첫 호출은 세 테이블을 한 번씩 Bulk Insert했다. 두 번째 호출은 기존 버전 1을 반환했고 Bulk Insert 호출 수는 3회에서 늘지 않았다. 입력 경로를 바꾼 세 번째 호출에서는 새 버전 2가 만들어지고 Bulk Insert 호출 수가 6회로 늘었다.

식별값 테스트에서 다음 결과를 확인했다.

- 같은 입력과 설정은 추천 행 순서가 달라도 같은 64자리 값
- 입력 경로나 임계값이 바뀌면 다른 값
- 경로가 같아도 파일 내용 해시가 바뀌면 다른 값
- 계산 상수가 바뀌면 다른 값
- 기록된 설정 해시와 실제 입력으로 다시 계산한 값이 다르면 DB 연결 전에 실패

## 결론

오류를 빨리 찾을 수 있는 검사는 추천 전에 배치했다. 결과 공개는 모든 계산과 임시 쓰기가 끝난 뒤로 미뤘다. 같은 성공 실행의 재시도는 기존 버전을 돌려주고, 결과에 영향을 주는 입력이 바뀐 실행만 새 버전으로 기록한다.

로컬 파일 두 개의 최종 이름 교체 사이에는 아주 짧은 간격이 남는다. 두 파일을 반드시 한 시점에 읽어야 하는 소비자가 생기면 파일 대신 버전 디렉터리와 완료 표식을 사용하는 방식을 검토해야 한다.
