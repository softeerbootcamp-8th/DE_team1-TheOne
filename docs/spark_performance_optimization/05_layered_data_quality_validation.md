# 정제부터 추천 적재까지 단계별 정합성 검사

- 요약
  - 형식이 맞는 행만 남겼다는 사실만으로는 Join 중 행 유실, 집계값 변형, 재고 초과를 찾을 수 없음
  - 원본 정제, Join 전후, 기사별 집계, 추천 시나리오, 데이터베이스 적재마다 서로 다른 검사를 배치
  - 원본 단계는 전체·통과·제외 건수를 한 번의 집계로 계산하고 기본 5% 이상 제외되면 중단
  - 67.5만 건 실측에서 정제 운행 합계와 기사별 집계 합계가 일치했으며, 회귀 테스트로 값 유실과 재고 초과를 재현

## 문제

데이터 품질 검사를 입력 스키마에만 걸면 변환 중에 생긴 오류를 찾지 못한다. 예를 들어 기사 차량 정보가 없는 운행은 Inner Join에서 조용히 사라질 수 있다. 행 수가 우연히 같아도 주행거리나 수익 값이 변형될 수 있다.

추천 결과는 행 수만 맞아도 틀릴 수 있다. 한 차량 모델의 추천 수가 실제 재고보다 많거나, 특정 알고리즘·임계값 조합에서만 기사가 빠질 수 있다.

Spark 작업이 센 제외 건수는 별도 프로세스에서 실행되는 작업 오케스트레이터가 직접 받을 수 없다. 로그에만 남기면 원본과 정제 결과의 행 수를 자동으로 대조하기 어렵다.

## 접근

모든 문제를 하나의 검사로 해결하지 않았다. 데이터가 의미를 바꾸는 지점마다 해당 단계에서만 확인할 수 있는 값을 검사했다.

- 원본에서 정제 데이터로 바뀔 때: 통과·제외 건수
- 큰 운행 데이터에 참조 정보를 붙이기 전: Join 키 누락
- 기사별 월 집계 직후: 거리·수익 합계 보존
- 추천 결과 저장 전: 기사 수, 재고, 순수익 조건
- 데이터베이스 커밋 전: 실제 적재 행 수

## 해결

원본 정제 단계는 필수값, 시간 순서, 거리·시간·금액 범위, 서비스 등급을 검사한다. 전체 행 수, 통과 행 수, 필수값 오류, 값 범위 오류, 등급 오류를 하나의 집계 Action으로 계산한다. 제외 행은 `전체 - 통과`로 계산한다. 한 행이 여러 사유에 걸릴 수 있으므로 사유별 건수를 더하지 않는다.

기본 제외 허용 비율은 5%다. 제외 비율이 임계값 이상이면 정제 결과를 사용하지 않는다. 계산한 건수는 데이터 파일을 쓴 다음 `_RECON.json`에 기록한다. 작업 오케스트레이터는 다음 식을 다시 확인한다.

```text
원본 행 수 = 정제 행 수 + 제외 행 수
```

Join 전에는 큰 데이터의 키가 작은 참조 데이터에 모두 있는지 `left_anti` Join으로 검사한다. 누락이 있으면 최대 5개의 키만 오류 메시지에 담는다. 기사와 차량 모델의 고유성, 재고의 음수 여부, 한 달의 연료비 날짜 수와 중복도 함께 검사한다.

기사별 집계를 만든 직후에는 정제 운행 기록의 주행거리, 기사 수익, 팁 합계를 다시 센다. 기사별 결과를 합한 값과 비교한다. 부동소수점 집계 순서가 달라질 수 있어 상대 오차 `1e-9`, 절대 오차 `1e-6`을 허용한다.

추천 결과는 알고리즘과 임계값 조합별로 나눠 검사한다. 각 조합에서 다음 조건을 확인한다.

- 기사별 한 행
- 입력 기사 수와 같은 결과 수
- 모델별 추천 수가 재고 이하
- 예상 기사 순수익 증가액이 0 이상

마지막으로 PostgreSQL에 넣은 뒤 커밋 전에 세 데이터의 행 수를 다시 조회한다. 예상 행 수와 다르거나 0행이면 트랜잭션을 실패시킨다.

## 검증

원본 정제 테스트는 정상 1행과 서로 다른 사유의 오류 3행을 넣었다. `total=4`, `valid=1`, `invalid=3`과 실제 정제 결과 1행이 일치하는지 확인했다. 제외 비율이 임계값과 같아도 실패하는 경계 조건도 검사했다.

`_RECON.json`이 데이터 파일 다음에 생성되는지 확인했다. 이전 실행의 대조 파일은 새 적재 전에 삭제되며, 대조 파일이 없으면 작업 오케스트레이터가 검사를 건너뛰지 않고 실패한다.

합계 대조 테스트에서는 다음 오류를 각각 재현했다.

- Join에서 운행 한 건이 빠짐
- 행 수는 같지만 주행거리 값이 달라짐
- 팁이 NULL일 때 원본과 집계가 모두 0으로 계산됨
- 허용 범위 안의 부동소수점 차이

실제 NYC 2026년 1월 데이터 67.5만 건에서는 주행거리, 기사 수익, 팁 합계 차이가 0.00이었다. 이 값이 다른 데이터에서도 항상 0이라고 가정하지 않아 코드에는 오차 허용 범위를 남겼다.

추천 불변식 테스트에서는 한 조합만 재고를 초과하는 경우, 한 조합만 음수 순수익을 만드는 경우, 한 조합만 기사가 빠지는 경우가 모두 실패하는지 확인했다. 데이터베이스 적재 테스트는 기대보다 적거나 많은 행, 0행을 커밋 전에 거부하는지 확인했다.

## 결론

입력 형식 검사만으로 끝내지 않고 변환 단계마다 잃을 수 있는 정보를 바로 비교했다. 원본 행 대조, Join 키, 금액 합계, 기사 수, 재고 수량, 적재 행 수가 서로 다른 오류를 잡는다.

검사 자체도 Spark Action을 만든다. 데이터가 더 커지면 품질 검사가 전체 실행 시간에서 차지하는 비율을 Spark UI로 확인하고, 같은 스캔에서 합칠 수 있는 집계만 합쳐야 한다. 오류 원인이 달라지는 검사를 무리하게 하나로 묶지는 않는다.
