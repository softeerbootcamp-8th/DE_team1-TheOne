# 문서 작성 원칙

`docs/`에는 **현재의 설계**, **결정의 근거**, **검증된 해결 방법**만 남깁니다.
모든 문서는 독자가 1분 안에 아래 네 가지를 찾을 수 있어야 합니다.

1. 무엇이 문제였는가
2. 무엇을 관측했는가
3. 무엇을 선택했는가
4. 어떻게 검증했는가

## 어디에 작성하는가

| 문서 성격 | 위치 | 기본 흐름 |
| --- | --- | --- |
| 파이프라인 설계·데이터 계약 | [`pipeline_design_and_data_quality/`](./pipeline_design_and_data_quality/) | 요약 → 구조·계약 → 검증 |
| 운영·신뢰성 정책 | [`pipeline_operations_and_reliability/`](./pipeline_operations_and_reliability/) | 문제 → 결정 → 동작 → 검증 |
| Spark 성능·구현 결정 | [`spark_performance_optimization/`](./spark_performance_optimization/) | 측정 → 원인 → 변경 → 전후 비교 |
| 장애 해결 기록 | [`troubleshooting/`](./troubleshooting/) | 증상 → 원인 → 해결 → 검증 |
| 제품 범위·완성도 | [`data_product_completeness/`](./data_product_completeness/) | 사용자 문제 → 동작 → 결과 → 한계 |
| 날짜별 논의 원본 | [`decision_making/`](./decision_making/) | 논의 → 결론 → 상세 기록 링크 |
| 긴 분석·발표용 서사 | [`blog/`](./blog/) | 배경 → 탐색 과정 → 결과 |

날짜별 회의 기록과 블로그는 근거 자료입니다. 현재 동작을 설명하는 공식 문서는 주제별
디렉터리에 작성하고, 원본 기록을 링크합니다.

## 공통 규칙

- **제목에 결론을 쓴다.** `Spark 최적화 정리`보다 `Broadcast Join으로 셔플을 줄임`이 낫습니다.
- **첫 화면에 요약을 둔다.** 요약은 결정·이유·검증 결과를 최대 3개 bullet로 씁니다.
- **문서 하나는 질문 하나만 다룬다.** 독립적으로 바뀔 내용은 문서를 나눕니다.
- **사실과 판단을 분리한다.** 로그·실행 계획·측정값을 먼저 쓰고 해석과 결정을 뒤에 씁니다.
- **전후를 숫자로 비교한다.** 환경과 입력 규모를 함께 적어 재현 가능한 수치로 만듭니다.
- **현재 상태를 본문에 쓴다.** 시행착오와 긴 로그는 접거나 `assets/`, 이슈, PR로 옮깁니다.
- **근거를 연결한다.** 관련 코드·테스트·대시보드·이슈·PR은 상대 경로로 링크합니다.
- **모르는 것은 단정하지 않는다.** 미검증 내용은 `가설`, 미구현 내용은 `후속 과제`로 표시합니다.

문단은 3문장 이내, 본문은 H2 6개 이내를 권장합니다. 런북과 블로그처럼 순서나 탐색
과정 자체가 필요한 문서는 예외입니다.

## 의사결정·성능 기록 템플릿

```md
# <선택한 결론>

## 요약

- <문제와 선택을 한 문장으로>
- <핵심 근거 또는 측정값>
- <검증 결과>

## 문제

<이 결정을 강제한 증상·요구·제약>

## 관측과 원인

- 관측: <측정값·로그·재현 조건>
- 원인: <관측으로 확인한 근본 원인>

## 선택

| 대안 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| <대안 A> |  |  | 선택/기각 이유 |
| <대안 B> |  |  | 선택/기각 이유 |

<무엇을 얻고 무엇을 포기했는지 한 문단으로>

## 검증

- 기준: <성공을 판별할 수치 또는 조건>
- 결과: <전 → 후>
- 재검토: <결정을 다시 열 조건>

## 근거

- 코드: [`path/to/code.py`](../path/to/code.py)
- 테스트: [`path/to/test.py`](../path/to/test.py)
- 이슈/PR: #<번호>
```

관측값이 없으면 성능 결정을 확정하지 않습니다. 결과가 예상과 다르거나 변경을 되돌렸다면
그 사실도 삭제하지 말고 `검증`에 남깁니다.

## 장애 해결 기록 템플릿

```md
# <원인과 해결이 드러나는 제목>

## 요약

- <증상>
- <확인한 원인>
- <해결과 결과>

## 문제

<영향 범위와 재현 조건>

## 원인

<로그 나열이 아니라 로그가 발생한 이유>

## 해결

<바꾼 코드·설정과 선택 이유>

## 검증

<재현 명령, 테스트 또는 전후 지표>

## 참고

<코드·이슈·PR·공식 문서 링크>
```

## 현재 설계·운영 문서 템플릿

```md
# <현재 보장하는 동작>

## 요약

- <현재 구조 또는 정책>
- <이 구조가 필요한 이유>
- <보장하는 결과>

## 구조 또는 정책

<현재 상태만 설명>

## 계약

<입력·출력·실패·재처리 조건>

## 검증

<이 설명과 구현이 일치함을 확인하는 방법>

## 참고

<관련 코드·테스트·결정 기록>
```

## 리뷰 체크리스트

- [ ] 제목과 요약만 읽어도 결론을 알 수 있는가
- [ ] 관측된 사실과 해석이 분리되어 있는가
- [ ] 숫자에 입력 규모·환경·비교 기준이 있는가
- [ ] 선택하지 않은 대안과 트레이드오프가 남아 있는가
- [ ] 검증 방법과 실제 결과가 있는가
- [ ] 코드·테스트·이슈·PR 링크가 유효한가
- [ ] 현재 구현과 충돌하는 과거 설명이 본문에 남아 있지 않은가
