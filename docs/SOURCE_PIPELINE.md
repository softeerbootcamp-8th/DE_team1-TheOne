# 원천 DB 파이프라인을 따로 만든 이유

합성 데이터를 만드는 일을 메인 파이프라인 안에 두지 않고, **별도 파이프라인 + HTTP API** 로 떼어 냈습니다.

---

## 문제 1 — 크롤링으로는 "지금"밖에 못 얻습니다

차량 카탈로그·배차 자격 같은 기준정보는 크롤링으로 가져올 수 있습니다.
그런데 **웹페이지는 현재 상태 하나만 보여줍니다.**
2025년 1월에 그 차가 얼마였는지, 그때 Comfort 자격이 있었는지는 어디에도 남아 있지 않습니다.

그래서 **백필을 테스트할 수가 없었습니다.**
배치 파이프라인에서 백필은 있으면 좋은 기능이 아니라 **반드시 동작해야 하는 경로**입니다 —
수집이 며칠 밀리거나, 변환 로직을 고쳐 지난 달을 다시 만들어야 하는 일이 계속 생깁니다.
그런데 원천이 과거를 기억하지 않으니 *"2025-01 을 다시 받아 와라"* 를 시켜 볼 대상 자체가 없었습니다.

## 문제 2 — 필요한 데이터가 애초에 공개되지 않습니다

이 제품은 *"이 기사가 이 차로 이만큼 벌었다"* 를 알아야 성립하는데,
공개된 TLC HVFHV 데이터에는 운행 기록만 있고 **`driver_id` 도 `taxi_id` 도 없습니다.**
"누가 어떤 차로 이 운행을 했는가"는 리스 업체 내부 시스템에만 있습니다.

---

## 결정 — 회사 시스템을 별도 파이프라인으로

| 만든 것 | 그래서 가능해진 것 |
| --- | --- |
| 내부 원장 (고객·차량·리스 계약) | 스냅샷 시점(`snapshot_date`)을 파라미터로 받아 **과거 어느 달이든 생성** |
| 기사-운행 배정 엔진 | TLC 실데이터에 `taxi_id` 를 시공간 제약하에 붙여 "누가 뭘 탔는가"를 생성 |
| 월별 릴리스 + HTTP API | *"지난 달을 다시 받아 와라"* 를 **실제로 시켜 볼 수 있는 원천** |

### 가짜 데이터라도 DAG 로 관리합니다

생성 스크립트를 손으로 돌리지 않고 Airflow DAG(`synthetic_driver_trip_source`)에 올렸습니다.
그래야 어느 달이 언제 만들어졌는지가 실행 이력으로 남고, 다시 만들 때도 같은 경로를 탑니다.

릴리스 ID 에 `seed` 를 박아 두어(`2025-01-seed-42`) **같은 입력이면 같은 산출물**이 나옵니다 —
백필을 돌려도 이전과 같은 데이터가 나오는지 대조할 수 있습니다.

### 결과 — 파이프라인 쪽이 진짜 문제를 풀게 됐습니다

파이프라인 코드 안에서 데이터를 만들었다면 "우리가 만든 걸 우리가 읽는" 구조라
수집 단계가 검증할 것도, 백필할 것도 없었을 겁니다.
API 경계를 두었기 때문에 **수집 · 검증 · 백필 · 멱등성**이 실제로 필요한 문제가 됐습니다.

---

## 생성 과정

TLC 원본에는 `driver_id` 도 `taxi_id` 도 없습니다. "누가 이 운행을 했는가"를 만들어 내는 단계입니다.

| 단계 | 내용 |
| --- | --- |
| ① 회사 상태 생성 | 고객 2,000명 · 차량 2,000대 · 리스 계약 2,000건. 성향 그룹별 기사 분포, 동시 활성 계약 금지 |
| ② 기사 성향 생성 | 시간대(3시간 8구간) 가중치, 선호 거리, 공항·맨해튼·등급 선호, 하루 목표 운행 수·근무 시간·최대 공차 시간 |
| ③ 구역 이동시간 집계 | TLC 265개 구역 간 실측 이동시간 **49,658쌍** — 공차 이동 가능 여부 판정에 사용 |
| ④ 후보 생성 | 기사를 10명씩 버킷으로 묶고, 운행을 해시로 **한 버킷에만** 배정 → 하드 제약(계약 유효·요일·시간대·차량 자격) 통과분에 선호 점수 부여 |
| ⑤ 배정 | (버킷 × 날짜) 단위 greedy 배정. 앞 운행 하차 구역 → 다음 승차 구역 이동시간, 일일 운행 한도, 총 근무 시간을 **모두** 만족해야 배정 |
| ⑥ 릴리스 | 운행/리스 두 데이터셋 + `manifest.json`(행 수 · SHA-256 · release_id) 게시 |
| ⑦ 서빙 | EC2 의 읽기 전용 HTTP API 가 월별 릴리스를 내려줌 |

**④에서 "운행마다 기사를 뽑는" 방향을 택하지 않은 이유**: 기사 2,000명이 한 달에 소화 가능한 운행은 약 117만 건으로
전체 트립의 **5.7%** 뿐입니다. 운행 기준으로 후보를 만들면 어차피 버려질 94.3% 에 대해서도 후보를 생성하게 됩니다.
