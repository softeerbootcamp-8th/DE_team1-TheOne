1. 지역 확장성 모델링 고려
    > 나중에 확장된다고 가정하면 어떤 것들을 추가 저장해야 할까?
    - 결론 : City,State도 함께 저장 (Eligible Cars(Uber), gas-price)
    - 사유 : 추후 뉴욕 외에 다른 지역으로도 확장할 가능성을 고려한 데이터 모델링 설계

2. Docker CI 시간 단축
    > CI에 시간이 너무 오래걸리는데 어떻게 단축하지?
    - 결론 : 런타임별로 러너를 나눠 병렬 빌드 (`docker-build` job matrix)
    - 사유 : docker build job이 매번 PR마다 런타임 3개를 순차로 빌드해 3분 이상 걸린다. 세 빌드는 서로 의존이 없어서 러너를 나누면 벽시계 시간이 셋의 합이 아니라 가장 느린 하나(airflow)가 된다.
    - 기각 : `setup-buildx-action` 레이어 캐시 — 처음에는 이 방향으로 결정했으나 실제로 붙여 보니 캐시 복원·저장 비용이 빌드보다 커서 오히려 느려져 접었다 (#184, `.github/workflows/ci.yml:136`). path 필터로 건너뛰는 방향도 uv 로 인해 PR이 멈춰서 기각.

3. ISSUE/PR skill 제작
    > ISSUE와 PR을 직접 작성해야 할까?
    - 결론 : Skill로 개발 외의 작업을 AI가 대신해주도록 제작
    - 사유 : ISSUE와 PR을 항상 직접 작성하기에 공수가 많이 들고, 사람이 쓰는 것보다 AI가 요약해서 쓰는 것이 읽기 더 편하다.
