# 8월 25일 의사 결정 목록

---

1. Source API 3종의 refresh 상태를 Bronze manifest로 일원화
   - 결정: `monthly_taxi_trip`, `driver_vehicle_monthly_snapshot`,
     `lease_vehicle_inventory`의 각 Bronze 버전에 `manifest.json`을 둔다.
   - 결정: manifest는 데이터 SHA-256·크기·행 수·계보와 GET 응답의 `ETag`,
     `Last-Modified`를 저장한다.
   - 결정: Airflow가 실제 Parquet과 manifest를 대조한 뒤에만 빈 `_SUCCESS`를 공개한다.
     manifest 누락·손상·불일치는 #984의 `run_quality_gate`를 통해
     `_QUARANTINED.json`으로 전환한다.
   - 결정: refresh는 최신 `_SUCCESS` Bronze manifest에서 조건부 HEAD validator를 읽고,
     별도 `mark_processed` 태스크와 `source_api_processed__*` Variable을 사용하지 않는다.
   - 결정: 세 `TriggerDagRunOperator`가 성공한 뒤 READY Asset을 한 번 발행한다. 모두
     skip하거나 하나라도 실패하면 발행하지 않는다.
   - 복구: manifest가 없거나 깨진 구형 버전은 정상 상태로 보지 않고 하위 DAG를
     재실행한다. 디렉터리 구조 데이터는 그대로 재사용하고, flat 구형 파일은 새
     `collected_at` 버전으로 한 번 이관한다.
   - 기각: 일일 refresh마다 원본 전체를 다시 내려받아 SHA-256을 비교하는 방식은
     조건부 HTTP가 제거하던 다운로드 비용을 되살린다.
   - 기각: SHA-256과 HTTP validator를 `_SUCCESS` 본문에 넣는 방식은 공개 marker와
     메타데이터 책임을 섞는다. `_SUCCESS`는 내용 없는 공개 여부로만 유지한다.
   - 변경: 8월 24일 3번의 “별도 manifest 계층은 과하다” 판단은 전체 데이터셋용
     lock 계층에는 유지하되, refresh 상태와 무결성을 함께 책임지는 API 3종 sidecar에는
     적용하지 않는다.
