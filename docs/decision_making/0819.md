1. AWS Glue Data Catalog·Apache Iceberg 도입 여부
    > 8/12 결정("Iceberg 도입 찬성")을 재검토
    - 결론 : 둘 다 미사용. Bronze·Silver는 일반 Hive Style Partitioning Parquet으로 S3에 저장
    - 사유 :
        - `schema/bronze`, `schema/silver`, `schema/gold` 패키지가 사실상 카탈로그 역할을 대신함 (이번 스키마 리팩토링으로 정리 완료)
        - Iceberg·Glue를 운영할 인력·학습 비용이 지금 팀 규모·데이터 규모에 안 맞음
        - 스키마 진화·버전 추적 필요성은 여전히 있지만, Iceberg 운영 부담이 그 이득보다 크다고 재판단
    - 영향 : 0812.md 3번("Iceberg 파티셔닝은 HVFHV에만")도 함께 무효화 — 전체 데이터셋이 Hive Style Partitioning만 사용

2. AWS 서비스별 파이프라인 매핑
    > 로컬 파이프라인(main/aws_lambda, main/spark, main/airflow)이 AWS 어떤 서비스에 대응하는지
    - 결론 :
        - Airflow → EC2(Private-App), 지금 docker-compose 구성 그대로
        - Bronze 수집 Lambda(`*_raw_to_bronze`) → 대부분 VPC 밖, S3·외부 API만 접근
        - Bronze→Silver 변환 → 대부분 Lambda(`*_bronze_to_silver`), HVFHV만 EMR(`main/spark/jobs/bronze_to_silver/hvfhv`)
        - Silver→Gold 변환 → EMR로 계산(`main/spark/jobs/silver_to_gold`), 결과는 별도 Lambda가 RDS에 적재
        - Bronze·Silver 저장 → S3, `year_month=YYYY-MM/` 파티션 그대로
        - Gold 저장 → RDS(Private-Data), `driver_aggregation`·`driver_car_suggestion`·`monthly_report` 테이블
        - Great Expectations → 별도 서비스 아님, Airflow 태스크 안에서 라이브러리로 실행 (`validate_bronze_task`/`validate_silver_task`)
        - Slack 알림 → 외부 웹훅, EC2에서 NAT 경유로 호출
    - 사유 : 지금 로컬 구조를 그대로 옮기는 게 마이그레이션 비용이 가장 적음

3. VPC 네트워크 구성
    > VPC·서브넷을 어떻게 나눌지
    - 결론 : VPC 1개, 가용영역(AZ) 2개, 3계층 서브넷(Public / Private-App / Private-Data) × 2AZ = 서브넷 6개
    - 사유 :
        - RDS는 서브넷 그룹에 최소 2개 AZ가 있어야 한다는 AWS 제약이 있음
        - 배치 파이프라인이라 AZ 3개까지는 불필요 — 하나 장애 나도 재시도로 감당
        - Private-Data(RDS)는 라우팅 테이블에 인터넷 경로 자체를 안 둬서 완전 격리

4. NAT Gateway 대신 NAT Instance 사용
    > 관리형 NAT Gateway는 시간당 요금 + 데이터 처리 요금이 있음
    - 결론 : EC2 기반 NAT Instance로 대체 (Amazon Linux 2023, iptables MASQUERADE + IP 포워딩)
    - 사유 : 비용 절감이 목적. 이 파이프라인은 트래픽량이 크지 않은 배치성이라 관리형 NAT의 관리 편의·확장성 이점이 크지 않음
    - 트레이드오프 : 단일 인스턴스라 그 인스턴스가 죽으면 private 서브넷의 아웃바운드 인터넷이 끊김 — 배치 재시도로 감당 가능하다고 판단해 감수

5. Lambda VPC 연결 정책
    > 모든 Lambda를 VPC 안에 넣을지
    - 결론 : RDS에 적재하는 Lambda만 VPC(Private-App)에 연결, 나머지(`*_raw_to_bronze`, `*_bronze_to_silver` 등)는 VPC 밖에 둠
    - 사유 : VPC 밖 Lambda가 콜드스타트가 빠르고 NAT 없이 인터넷·S3에 바로 접근 가능. VPC 연결은 RDS처럼 VPC 전용 리소스에 접근해야 할 때만 필요
    - 참고 : 회사 원천 시스템(synthetic source API)을 private subnet에 올리면, 그걸 크롤링하는 Lambda(HVFHV·driver_vehicle_monthly_snapshot·lease_vehicle_inventory 등)도 VPC 연결이 필요해짐 — 배포 위치 확정 시 재검토

6. Private 서브넷의 S3 접근 경로
    > Private 서브넷에서 S3로 가는 트래픽을 어떻게 보낼지
    - 결론 : S3 Gateway VPC 엔드포인트 사용 (NAT를 안 거침)
    - 사유 : Gateway 타입은 라우팅 테이블 기반이라 무료이고, 이 파이프라인 트래픽 대부분이 S3(Bronze/Silver 적재)라 NAT 비용을 크게 줄임
