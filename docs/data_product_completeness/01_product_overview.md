# 01. 무엇을 만들었나

- 요약
  - 리스 업체 담당자가 "차를 바꾸면 더 벌 기사"를 감으로 골라내고 있었다
  - 한 달 운행 기록으로 기사별 교체 효과를 계산해, 기사와 회사가 **동시에** 이득인 조합만 골라 보여준다
  - 기사 2,000명 × 보유 차량 12종 조합을 계산해 월 단위로 갱신한다

## 사용자와 문제

뉴욕에서 Uber·Lyft 기사에게 차량을 리스해 주는 업체의 **고객 담당자**가 씁니다.

이 담당자는 계약 중인 기사 2,000명 가운데 "차를 바꾸면 더 벌 사람"을 골라 전화해야 합니다. 그런데 고를 기준이 없어서 감으로 뽑았습니다. 그러면 두 가지를 놓칩니다.

- 기사는 더 벌 수 있는데 그대로 둔다.
- 회사는 더 비싼 차를 리스해 매출을 올릴 기회를 놓친다.

**추천 대상은 두 조건을 동시에 만족해야 합니다.**

- 기사의 예상 월 순수익이 하한 이상 오른다 (기본 $500).
- 회사가 받는 월 리스료도 오른다.

한쪽만 오르면 뺍니다. 기사만 이득이면 회사가 남길 게 없고, 회사만 이득이면 기사가 차를 바꿀 이유가 없습니다.

## 담당자가 쓰는 순서

1. 대시보드를 열고 운영 지역과 대상 월을 고른다. 추천 알고리즘과 순수익 증가 하한은 기본값이 이미 잡혀 있다.
2. 상단 지표에서 이번 달에 몇 명에게 전화하면 되는지, 1인당 얼마나 오르는지 본다.
3. 하한을 올리거나 내려 목록 크기를 조절한다.
4. 목록에서 기사를 클릭해 현재 차량과 추천 차량을 비교하고, **추천 사유**를 보고 통화 내용을 준비한다.
5. 목록을 CSV 로 내려받아 통화 리스트로 쓴다.

## 기획한 기능이 어디에 구현됐나

기획 문서의 해결방안은 "차량 변경 시 기사 순수익 월 $500 이상 증가 & 리스 업체 렌탈 객단가 상승인 조합만 추천" 입니다. 그것을 나눠 구현한 결과입니다.

| 기획 요구 | 구현 |
| --- | --- |
| 기사별 현재 운행 수익 파악 | 한 달 운행 기록을 기사 단위로 모아 현재 차량 기준 순수익을 계산 |
| 차량 교체 효과 계산 | 기사 2,000명 × 보유 차량 12종의 예상 연료비·리스료·순수익을 각각 계산 |
| "순수익 증가 & 매출 증가" 게이트 | 추천 알고리즘이 배정 단계에서 걸고, 대시보드가 화면에서 한 번 더 좁힘 |
| 누구에게 먼저 전화할지 | 순수익 증가액 순으로 정렬한 목록 + 행을 누르면 열리는 상세 비교 |
| 판단 근거 제시 | 조합마다 추천 사유 문장을 함께 저장, 선정 과정을 산점도로 표시 |
| 결과를 믿을 수 있는가 | 저장 전 금액 합계·재고 한도 검증, 어떤 입력으로 계산했는지 화면에 노출 |

## 추천 알고리즘 — 기사 우선에서 회사 우선으로

알고리즘 버전은 **골라 쓰는 옵션이 아니라 개선된 순서**입니다. 로직이 바뀔 때만 번호를 올리고, 올라간 뒤에는 그 번호가 현행입니다. 지금 현행은 **v2** 입니다.

| 버전 | 배정 1순위 | 통과 조건 | 상태 |
| --- | --- | --- | --- |
| v1 | 기사 순수익 증가 | 회사 매출 증가가 0보다 큼 | 대체됨 |
| v2 | 회사 매출 증가 | 기사 순수익 증가가 하한 이상 | **현행** |

**왜 바꿨나.** v1 은 회사 매출 증가를 "0보다 크면 통과"로만 걸렀습니다. 매출이 $1 만 올라도 통과합니다. 차량 재고가 한정돼 있으니 누군가에게 배정하면 다른 사람은 못 받는데, v1 은 기사 순수익이 큰 사람부터 채우므로 **회사에 더 이득인 배정을 순위에 밀려 놓칠 수** 있었습니다.

v2 는 순위를 뒤집었습니다. 회사 매출 증가가 큰 쪽부터 채우고, 기사 쪽은 "하한 이상"이라는 바닥선을 통과 조건으로 둡니다. 하한이 0보다 크므로 바꿔서 손해를 보는 배정은 애초에 통과하지 못합니다.

하한은 한 값만 쓰지 않고 **$100·$200·$300·$400·$500 다섯 개를 각각 계산해 따로 저장**합니다. 담당자가 화면에서 하한을 바꿀 때 다시 계산하지 않아도 되고, "하한을 낮추면 몇 명 늘어나는지"를 바로 볼 수 있습니다.

두 버전 모두 **차량 재고를 넘기지 않게 배정**합니다. 후보를 순위대로 세우고, 한 바퀴 돌 때마다 남은 재고만큼만 채웁니다. 전체를 놓고 최적해를 푸는 방식이 아니라 순위 높은 쪽부터 채우는 방식입니다.

코드는 매 실행마다 v1 도 함께 계산해 저장합니다. 화면이 최신 버전을 기본값으로 잡으므로 담당자가 보는 것은 항상 v2 이고, v1 결과는 번호를 올린 근거를 나중에 대조하려고 남겨둔 이력입니다.

### 추천 사유

해당하는 항목을 쉼표로 이어 붙입니다.

| 사유 | 조건 |
| --- | --- |
| `렌트비 절감` | 추천 차량의 월 리스료가 현재보다 낮음 |
| `연료비 절감` | 예상 월 연료비가 현재보다 낮음 |
| `Comfort(Uber) 등급 가능` | 지금은 자격이 없고 추천 차량으로는 생김 |
| `Extra Comfort(Lyft) 등급 가능` | 위와 같음 |
| `현재 차량 유지` | 추천이 현재 차량인 경우 |
| `예상 순수익 개선` | 위 어느 항목도 해당하지 않을 때 |

예: `연료비 절감, Comfort(Uber), Extra Comfort(Lyft) 등급 가능`

## 무엇을 넣고 무엇이 나오나

### 입력

| 출처 | 데이터 | 규모 | 주기 |
| --- | --- | --- | --- |
| 회사 원천 API | 월별 택시 운행 기록 | 월 70–90만 건 | 일 1회 |
| 회사 원천 API | 기사별 현재 차량·계약 스냅샷 | 약 2,000행 | 일 1회 |
| 회사 원천 API | 리스 보유 차량 목록(등급 자격·연비·주간 리스료·보유 대수) | 12종 | 일 1회 |
| 미국 에너지정보청(EIA) | 뉴욕주 휘발유 주간 소매가 | 월 1건 | 월 1회 |
| 미국 에너지정보청(EIA) | 뉴욕주 전기 요금 | 월 1건 | 월 1회 |

운행 기록의 원본은 뉴욕시가 공개하는 실데이터입니다. 다만 거기에는 어느 기사가 어느 차로 운행했는지가 없어서, 별도 파이프라인이 제약 조건 안에서 기사·차량 식별자를 붙여 가상의 회사 데이터베이스로 만들어 API 로 내보냅니다.

### 출력

결과는 PostgreSQL 데이터베이스에 저장되고 대시보드가 읽습니다. **운영 지역과 대상 월마다 실행 회차(버전)가 쌓입니다** — 같은 달을 다시 계산하면 이전 결과를 지우지 않고 다음 회차로 붙습니다.

| 결과 | 한 행 | 월 규모 | 담긴 것 |
| --- | --- | --- | --- |
| **기사별 한 달 운행 실적** | 기사 1명 | 약 2,000 | 등급 자격, 현재 차량과 연비, 월 주행거리·정산액·팁·연료비·리스료·순수익 |
| **기사별 추천 차량 결과** | 기사 × 알고리즘 × 하한 | 최대 12,000 | 추천 차량, 추천 사유, 예상 연료비·순수익, **기사 순수익 증가액**, **회사 매출 증가액** |
| **계산에 쓴 입력 기록** | 실행 1회 | 1 | 어떤 입력 파일과 어떤 코드 버전으로 계산했는지 |

추천 결과가 12,000행인 이유는 기사 2,000명에 알고리즘·하한 조합 6개(v1 한 개 + v2 다섯 개)를 곱한 값입니다.

같은 입력과 같은 설정으로 다시 돌리면 새 회차를 만들지 않고 기존 결과를 그대로 씁니다. 입력이 바뀌면 새 회차가 생깁니다.

## 계산 방법

운행 1건 단위 값을 기사·월 단위로 모아 계산합니다.

- **월 연료비** — 휘발유차는 `Σ(운행거리 × 그날 유가) ÷ 연비`. 전기차는 `Σ(운행거리 × 그날 전기요금) × 33.7 ÷ 연비`. 33.7 은 휘발유 1갤런에 해당하는 전력량(kWh)입니다.
- **월 리스료** — `주간 리스료 × (그 달 일수 ÷ 7)`
- **월 순수익** — `플랫폼 정산액 + 팁 − 월 연료비 − 월 리스료`
- **상위 등급 전환 수익** — 차를 바꾸면 Comfort·Extra Comfort 운행을 받을 수 있게 됩니다. 다만 자격이 생겨도 전부 상위 등급으로 잡히지는 않으므로 **일반 운행의 30% 만 전환된다고 가정**합니다. 단가는 플랫폼별·운행거리 구간별(0-2 / 2-5 / 5-10 / 10-20 / 20+ 마일) 실측 배수를 씁니다.
