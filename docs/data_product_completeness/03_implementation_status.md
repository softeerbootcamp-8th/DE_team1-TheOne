  - 추천 계산이 맞는지는 확인하지만, 그 추천이 좋은 추천인지는 확인할 수 없다

## 결과물이 어떻게 생겼나

추천 결과 한 행이 통화 한 건에 필요한 것을 다 담습니다.

| 담당자의 질문 | 답하는 값 |
| --- | --- |
| 누구에게 전화하나 | 기사 식별자 |
| 무엇을 권하나 | 추천 차량의 제조사·모델·연식 |
| 왜 그 차인가 | 추천 사유 문장 — 예: `연료비 절감, Comfort(Uber), Extra Comfort(Lyft) 등급 가능` |
| 기사에게 무슨 이득인가 | 예상 월 순수익 증가액 |
| 회사에 무슨 이득인가 | 예상 월 리스료 증가액 |
| 근거 수치는 | 추천 차량의 월 리스료, 예상 월 연료비, 예상 월 순수익 |
| 어떤 기준으로 뽑혔나 | 알고리즘 버전과 순수익 증가 하한 |
| 어떤 데이터로 계산했나 | 계산에 쓴 입력 파일 경로와 코드 버전 |

**두 증가액이 함께 양수인 행만 남습니다.** 리스료가 올라도 연료비 절감과 상위 등급 수입이 그보다 크면 기사 순수익도 오릅니다. 한쪽만 오르는 조합은 배정 단계에서 빠집니다.

기사 상세는 현재 차량과 추천 차량을 월 리스료·월 연료비·월 순이익 세 가지로 나란히 놓습니다. 단위가 달라 한 차트에 합치지 않고 셋으로 쪼갰습니다.

전체 화면은 [01 무엇을 만들었나](./01_product_overview.md#결과물-형태) 하단 이미지에 있습니다.

### 한 달 산출 결과

2026년 5월, 뉴욕, 하한 $100 기준으로 화면에 뜬 값입니다.

| 지표 | 값 |
| --- | --- |
| 분석 대상 기사 | 2,000명 |
| 추천 대상 기사 | **162명** (8.1%) |
| 기사 1인당 예상 월 순수익 증가 | **$192** |
| 회사 평균 예상 월 리스료 증가 | **$241** |
| 회사 예상 월 리스료 증가 합계 | **$39.1K** |
| 추천 차종 수 | 6종 |

162명 × $241 = 약 $39.1K 로, 화면의 합계와 1인당 값이 맞습니다.

차종 이동을 보면 현재는 준중형 세단(KIA FORTE)이 가장 많고, 추천은 SUV(CHEVROLET EQUINOX · KIA SPORTAGE · CHEVROLET TRAVERSE · TOYOTA RAV4) 쪽으로 몰립니다. 연비가 크게 나쁘지 않으면서 상위 등급 자격이 생기는 차량이 두 조건을 함께 만족하기 때문입니다.

**하한을 낮추면 대상이 늘어납니다.** 위 값은 하한 $100 기준입니다. 기본값인 $500 으로 올리면 대상 인원이 줄고 1인당 증가액은 올라갑니다. 다섯 개 하한을 미리 계산해 저장하므로 화면에서 바꿔 보면 바로 나옵니다.

> 저장소의 로컬 CSV(`data/gold/`)는 2026-08-18 잔재로, 지금은 없는 월간 요약 결과와 옛 컬럼명이 들어 있습니다. 현재 결과의 근거로 쓸 수 없으니 로컬에서 확인하려면 [02 집계·추천만 따로](./02_e2e_pipeline.md#집계추천만-따로)로 다시 만들어야 합니다.

## 안 되는 것

| 제약 | 내용 | 담당자에게 미치는 영향 |
| --- | --- | --- |
| 전기 요금 공개 지연 | 미국 에너지정보청의 전기 요금이 약 3개월 늦게 확정됩니다. 연료비 표가 그만큼 물러선 달을 채우므로 분석 대상 월도 함께 밀립니다 | 최신 달 추천은 확정 전 잠정값 기준일 수 있습니다. 어떤 버전으로 계산했는지는 화면에서 확인할 수 있습니다 |
| 운영 지역 하나 | 지역 축과 경로 규약은 확장을 열어 뒀지만 실제 데이터와 운영은 뉴욕 하나입니다 | 다른 도시로 넓히려면 원천 데이터 생성 쪽부터 손대야 합니다 |
| 동시 실행 상한 3 | Airflow 가 EC2 한 대에서 돌아 동시 실행이 3개로 묶여 있습니다 | 지역이 3개를 넘으면 나머지는 큐에서 기다립니다 |
| 합성 원천 | 뉴욕시 공개 데이터에는 어느 기사가 어느 차로 운행했는지가 없어, 제약 조건 안에서 식별자를 붙여 만든 가상 회사 데이터를 씁니다 | 실제 리스 업체 원장과 배정 분포가 다를 수 있습니다. 운행 기록 자체는 실데이터입니다 |
| 월 단위 갱신 | 추천은 월 단위로만 계산됩니다 | 당일 운행 변화는 반영되지 않습니다. 리스 계약 판단은 월 단위라 지금은 문제되지 않습니다 |
| 과거 회차 비교 화면 없음 | 대시보드는 지역·월별 최신 회차만 조회합니다 | 이력은 데이터베이스에 남아 있어 대조는 가능하지만 화면에서 비교할 수는 없습니다 |
| 스키마 변경 수동 | 데이터베이스 구조가 바뀌면 배포 **전에** 사람이 SQL 을 실행해야 합니다 | 실행을 잊으면 정리 작업이 실패합니다. 실제로 한 번 겪었습니다 |
| 알고리즘 설명 수동 | 알고리즘 버전별 설명 표는 파이프라인이 채우지 않습니다 | 새 알고리즘을 넣어도 사람이 행을 추가하기 전까지 화면에 설명이 안 뜹니다 |
| **추천의 타당성은 확인 못 함** | 확인하는 것은 **구조**입니다 — 재고를 넘기지 않았는지, 기사가 중복되지 않았는지, 금액 합계가 보존됐는지, 조인 키가 맞는지, 증가액이 음수가 아닌지 | 산식과 가정이 맞다면 계산은 맞습니다. 그러나 기사가 실제로 차를 바꿨을 때 예상대로 버는지는 확인할 수 없습니다. 원천이 합성 데이터라 사후 관측 자체가 불가능합니다 |
