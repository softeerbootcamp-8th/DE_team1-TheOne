# 최신 정상 데이터는 남기고 오래된 버전은 90일 후 정리

- 요약
  - 원천 수정과 품질 검사 실패가 반복될 때마다 데이터 버전이 생겼지만, 오래된 버전을 지우는 작업이 없어 계속 누적됐다.
  - 운영 지역과 대상 월마다 최신 정상 버전은 남기고, 90일이 지난 이전 정상 버전과 실패 버전을 매일 삭제하도록 변경했다.
  - S3의 원본·정제 데이터와 RDS의 최종 데이터를 각각 정리하며, dry-run과 부분 실패 처리를 자동화 테스트로 확인했다.

## 문제

수집한 원본 데이터(Bronze)와 정제된 데이터(Silver)는 원천을 받은 시각별로 새 버전을 만든다. 기존 파일을 덮어쓰지 않으므로 이전 결과와 비교하거나 문제가 생겼을 때 직전 데이터로 돌아갈 수 있다.

품질 검사를 통과한 버전에는 `_SUCCESS` 파일이 생긴다. 실패한 버전에는 실패 시각과 원인이 담긴 `_QUARANTINED.json` 파일이 생긴다. 이후 작업은 `_SUCCESS`가 있는 데이터만 읽는다.

그러나 버전을 추가하는 규칙만 있고 지우는 규칙은 없었다. 원천 수정과 재처리가 반복될수록 사용하지 않는 과거 정상 버전과 품질 검사에 실패한 데이터가 계속 남았다.

대시보드에서 사용하는 최종 데이터(Gold)도 같은 지역과 월을 다시 계산할 때마다 RDS에 정수 버전을 하나씩 추가했다. 대시보드는 최신 버전만 읽었지만 이전 버전은 계속 남았다.

S3에 생성 후 90일 만료 규칙만 적용할 수도 없었다. 원천이 90일 넘게 바뀌지 않으면 마지막 정상 데이터도 함께 삭제될 수 있다. 이 데이터는 다음 작업이 읽을 수 있는 유일한 정상본일 수 있다.

운영자가 S3 콘솔에서 직접 지우는 방식도 사용하지 않았다. S3에서 폴더처럼 보이는 구조는 같은 문자열로 시작하는 객체 묶음이다. 삭제 범위를 잘못 선택하면 다른 지역이나 대상 월의 데이터까지 지울 수 있다.

## 접근

삭제 여부는 개별 파일이 아니라 한 번의 수집 또는 정제 결과가 들어 있는 버전 단위로 판단했다.

- 이전 정상 버전은 생성 후 90일 동안 남긴다.
- 실패 버전은 실패 시점부터 90일 동안 남긴다.
- 운영 지역과 대상 월별 최신 정상 버전은 저장 계층과 생성 시각에 관계없이 남긴다.

정리 작업은 데이터 수집 작업에 넣지 않고 별도의 일일 Airflow 작업으로 분리했다. 수집이 오랫동안 실행되지 않은 지역과 월도 같은 기준으로 확인해야 하기 때문이다.

## 해결

일일 Airflow DAG는 S3 정리와 RDS 정리를 별도 태스크로 실행한다. 한 저장소의 장애가 다른 저장소의 정리를 막지 않으며, DAG 자체는 동시에 한 번만 실행된다.

S3 정리 태스크는 원본 데이터와 정제된 데이터를 조회한다. 경로에 기록된 수집 시각을 읽고, 운영 지역과 대상 월이 같은 버전끼리 묶는다.

각 묶음에서 `_SUCCESS`가 있는 가장 최신 버전을 먼저 찾는다. 이 버전은 90일이 지나도 삭제하지 않는다. 나머지 정상 버전은 생성 후 90일이 지난 경우에만 삭제한다.

`_QUARANTINED.json`이 있는 버전은 파일 안의 실패 시각을 확인한다. 실패 후 90일이 지났다면 상태 파일만 지우지 않고 같은 버전 경로에 있는 데이터 파일도 함께 삭제한다.

```text
삭제 대상 = 90일이 지난 이전 정상 버전
         또는 실패 후 90일이 지난 실패 버전

보호 대상 = 운영 지역·대상 월별 최신 정상 버전
         또는 생성·실패 후 90일이 지나지 않은 버전
```

경로의 버전 시각을 해석할 수 없거나 `_SUCCESS`와 `_QUARANTINED.json`이 함께 있으면 삭제 전에 작업을 실패시킨다. 상태를 추측해서 지우지 않기 위해서다.

수동 실행 시 dry-run을 선택하면 삭제 후보 경로와 객체 수만 계산한다. 실제 삭제는 S3 요청 한 번에 최대 1,000개씩 나눠 처리한다. 응답에 실패한 객체가 하나라도 있으면 Airflow 작업을 실패로 기록해 재시도한다.

Airflow 실행 역할에는 버킷 목록 조회 권한과 `bronze/`, `silver/` 아래 객체 삭제 권한이 필요하다. 권한이 빠져 있으면 부분 삭제 응답을 성공으로 처리하지 않고 작업을 실패시킨다.

RDS에는 Gold 적재 한 번당 한 행을 남기는 버전 메타데이터 테이블을 추가했다. 지역, 대상 월, 버전, 생성 시각을 기록한다. Gold 데이터 2종의 행 수 검증이 끝난 뒤 같은 트랜잭션에서 메타데이터를 기록하므로, 실패한 적재는 정리 대상 이력에 들어가지 않는다.

RDS 정리 태스크는 지역과 월마다 가장 높은 버전 번호를 보호한다. 나머지 버전 중 메타데이터의 생성 시각이 90일을 지난 버전만 두 Gold 테이블에서 삭제한다. 두 테이블과 메타데이터 삭제는 한 트랜잭션으로 묶었다. 중간에 하나라도 실패하면 앞서 실행한 삭제도 롤백된다.

기존 Gold 행에는 생성 시각이 없었다. 마이그레이션은 기존 버전을 마이그레이션 실행 시각에 생성된 것으로 기록한다. 실제 생성 시각을 추측해 즉시 지우지 않고 기존 이력을 90일 더 남기는 선택이다.

## 적용 전후 비교와 검증

| 구분 | 적용 전 | 적용 후 |
|---|---|---|
| 이전 정상 버전 | 기간 제한 없이 누적 | 최신 정상본을 제외하고 90일 후 삭제 |
| 실패 데이터 | 데이터와 실패 기록이 계속 누적 | 실패 시점부터 90일 후 버전 전체 삭제 |
| 최신 정상본 | 단순 만료 규칙에서 삭제될 수 있음 | 지역·월마다 한 개를 날짜와 관계없이 보호 |
| RDS 최종 데이터 | 대시보드가 읽지 않는 이전 버전도 누적 | 생성 시각을 기록하고 90일 후 두 테이블에서 함께 삭제 |
| 실행 방식 | 운영자가 경로를 골라 직접 삭제 | 하루 한 번 별도 작업으로 실행 |
| 삭제 오류 | 일부 객체 누락을 따로 확인해야 함 | S3 응답의 부분 실패도 작업 실패로 처리 |

자동화 테스트에서는 다음 동작을 확인했다.

- 정확히 90일이 지난 이전 정상 버전은 삭제하고 최신 정상본은 남겼다.
- 최신 정상본만 있는 다른 운영 지역의 데이터는 90일이 지나도 남겼다.
- 실패 후 90일이 지난 경로에서는 중첩 파일과 상태 파일을 함께 삭제했다.
- 90일이 지나지 않은 실패 버전은 남겼다.
- dry-run에서는 후보를 계산하지만 삭제 요청을 보내지 않았다.
- 1,001개 객체를 1,000개와 1개로 나누어 삭제했다.
- S3가 일부 객체의 삭제 실패를 반환하면 작업이 실패했다.
- 같은 정리 작업을 다시 실행하면 삭제 후보가 없는 상태로 끝났다.
- RDS에서는 지역·월별 최신 버전을 제외하는 조회 조건을 확인했다.
- RDS의 두 Gold 테이블과 버전 메타데이터에서 같은 버전을 삭제하는지 확인했다.
- 두 번째 Gold 테이블 삭제가 실패하면 트랜잭션이 롤백되는지 확인했다.
- Gold 적재 행과 생성 시각 메타데이터가 같은 트랜잭션에 기록되는지 확인했다.
- 일일 실행, catchup 비활성화, 동시 실행 한 개와 S3·RDS 태스크 분리를 확인했다.

## 결론

새 버전을 만드는 규칙에 90일 정리 작업을 연결했다. 최근 데이터와 지역·월별 최신 정상본은 남고, 확인 기간이 지난 S3 버전 폴더와 RDS Gold 버전 행은 삭제된다.

로컬 개발 환경의 Gold CSV는 지역과 월마다 같은 파일을 덮어쓰므로 별도 구버전이 생기지 않는다. 자동 정리 대상은 운영 RDS다.

S3 버전 관리가 켜진 버킷에서는 일반 삭제가 과거 객체 버전까지 제거하지 않는다. 과거 `VersionId`까지 삭제해야 한다면 버킷의 버전 관리 설정과 별도 만료 규칙을 함께 검토해야 한다.
