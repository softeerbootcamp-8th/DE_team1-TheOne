# 원천 수정 이력과 처리 완료 상태 분리

- 요약
  - 문제 : Overwrite시 `변경`/`재시도`/`처리 중` 상태를 구분할 수 없음.
  - 접근 : 
    1. 가상 회사 DB 수집 : 원천 내용이 달라질 때만 새 버전 생성(SHA-256 비교 후 적재)
      - 가상 회사 DB는 과거 기록이 변경될 수 있음
    2. 어떤 원천에서 파생됐는지 기록 (지역-날짜-시기별 파티셔닝)
    3. 품질 검증을 통과한 버전만 공개 (검증된 데이터만 후속 단계로 넘어가도록)
  - 검증 : 각 문제 상황을 시나리오로 작성 후, 자동화 테스트 진행

## 문제
- 배경 
  1. 원천 데이터가 수집된 뒤에도 내용이 수정될 수 있음
  2. 실행만 다시 되고 내용은 변경되지 않았을 수 있음
- 문제 
  1. Overwrite하면, 이전 원천으로 만든 결과 확인 불가
  2. 항상 새 파일 생성 시 
    - 같은 내용 중복
    - 불필요한 후속 계산 
  3. 파일 존재만으로 완료 여부 판단 시 아래 문제에도 후속 계산 진행
    - 품질 검증 실패 / 데이터 일부만 써짐

## 접근
> 상태 따로 관리
- 3가지 상태 관리
  - **원천 정보**: 언제 수집한 어떤 원천인가
  - **실제 내용 변경 여부**: 직전 완료본과 내용이 다른가
  - **공개 여부**: 후속 계산이 읽어도 되는가
- 대시보드 규칙 : 완료된 버전 중 최신 선택 (단순 최신 파일 X)

## 해결
1. **원천 정보 관리**
  - 원본 데이터 아래 규칙에 따라 저장
    ```bash
    S3
    └─ 운영지역
        └─ YYYY-MM
              └─ Datatime
                    |- xxxx.parquet
                    └─ _SUCCESS    
    ```
2. **실제 내용 변경 여부 관리**(저장 후 아래 과정 진행)
  1. 읽기 가능 여부 확인
  2. 직전 완료본과 SHA-256 비교 (내용 동일 여부 확인)
    - 같으면, 기존 데이터 재사용(저장 X)
    - 다르면, 새 수집 버전 저장 후 이전 버전 남김
  3. 정제 데이터 경로에 원천 수집 버전 기록
    - if, 원천 두 개 합친 경우엔 **두 입력 버전 함께 기록**
3. **공개 여부 관리**
  > 파일 작성 완료 여부와 공개 여부 분리
  - 품질 검증 통과 : 파티션에 _SUCCESS(완료 표시 오브젝트)를 추가
    - 동일 데이터 재처리 시, 기존 _SUCCESS 제거 후, 진행
  - 품질 검증 실패 : 파티션에 _QUARANTINED.json(실패 사유 파일) 추가

## 검증
> 테스트 생성 후 검증
- 아래 시나리오별 테스트를 만들어 확인
  - 변경 여부에 따른 확인
    - 변경 : **새 수집 버전으로 추가**되는지 확인
    - 동일 : 기존 버전을 재사용하는지 확인
  - 공개 여부 관리
    - 품질 검증 실패 : quarantined.json 파일 생성 확인
    - 최신 완료본 선택 : 완료된 것 중 최신을 선택하는지 (미완료된 최신 데이터를 선택하지 않는지)
  - 재시도
    - **완료 표시 제거** : 재처리 시, 작성 전에 기존 완료 표시 지우는지 확인
    - **미완료시 완료 표시 없음** : 쓰기 실패 시 완료 표시가 안 생기는지 확인
  - 입력 버전 구분
    - 여러 원천을 합친 결과가 원천별 버전 변경 구분하는지 확인
  - 그 외 다수.

## 결론

- 현재
  - SHA-256을 계산하여 변경된 경우 추가 적재
  - 구버전 데이터와 실패 데이터 보존 기간 정책 설정 (90일)
    - 구버전 데이터 : 롤백 대비용 (롤백 필요 검토는 90일이면 충분하다 판단)
    - 실패 데이터 : 실패 원인 분석용 (원인 분석 또한 90일이면 충분하다 판단)
- 원천 파일 개수 증가 시, `원격 체크섬과 함께 사용` 필요
