# 같은 데이터 재처리로 최종 버전이 중복 생성되는 문제 해결

- 요약
  - 데이터베이스 반영은 끝났지만 작업 성공 응답이 유실되면, 재시도에서 같은 최종 데이터가 새 버전으로 한 번 더 저장될 수 있었다.
  - 정제된 데이터 4종의 버전 경로와 추천 계산 설정을 SHA-256으로 변환해 같은 실행을 식별하도록 변경했다.
  - 회귀 테스트에서 같은 실행을 두 번 호출해도 데이터 입력은 최초 3회에서 늘지 않았고, 입력 버전이 바뀌었을 때만 다음 버전을 만들었다.

## 문제

대시보드에서 사용하는 최종 데이터(Gold)는 기사별 한 달 운행 실적, 기사별 추천 차량 결과, 계산에 사용한 입력 데이터 이력을 한 번에 데이터베이스에 저장한다. 같은 운영 지역과 대상 월을 다시 계산하면 이전 결과를 남긴 채 다음 버전을 만든다.

세 결과는 하나의 트랜잭션으로 저장했다. 하나를 저장하다 실패하면 앞서 저장한 결과도 취소됐다. 그러나 트랜잭션만으로는 데이터베이스 반영 이후의 통신 오류를 처리할 수 없었다.

예를 들어 데이터베이스는 반영을 마쳤지만 작업 실행기가 성공 응답을 받기 전에 연결이 끊길 수 있다. 실행기는 실패로 판단해 같은 작업을 재시도한다. 기존 코드는 가장 높은 버전에 1을 더했으므로 내용이 같은 결과가 두 버전으로 남았다.

이 중복은 일부 데이터가 잘못 저장된 상태는 아니다. 다만 대시보드가 읽지 않는 버전이 늘어나고, 운영자는 입력이 바뀌어 새 버전이 생긴 것인지 재시도 때문에 중복된 것인지 구분하기 어려웠다.

## 접근

재시도에서 같은 계산인지 판단하려면 실행마다 바뀌지 않는 값이 필요했다.

작업 실행기의 실행 번호는 사용하지 않았다. 한 실행 안의 재시도는 구분할 수 있지만, 같은 입력을 수동으로 다시 실행하면 번호가 달라지기 때문이다.

최종 결과 전체를 해시하는 방법도 제외했다. 기사별 결과를 다시 직렬화하고 읽어야 하므로 결과 크기만큼 추가 작업이 생긴다.

대신 계산 결과를 결정하는 다음 정보를 사용했다.

- 운영 지역과 대상 월
- 정제된 데이터 4종의 버전 경로
- 추천 알고리즘 버전과 임계값 조합

이 정보를 키 순서가 일정한 JSON으로 만든 뒤 SHA-256 값을 계산했다. 추천 결과의 행 순서가 달라도 알고리즘과 임계값 조합을 정렬하므로 같은 값이 나온다.

정제된 데이터의 버전 경로는 완료된 뒤 내용이 바뀌지 않는다는 현재 저장 규칙을 따른다. 추천 로직을 바꿀 때는 기존 규칙대로 알고리즘 버전도 올려야 한다.

## 해결

최종 데이터의 버전 이력에 64자리 SHA-256 값을 함께 기록했다. 같은 운영 지역과 대상 월에서는 이 값이 중복될 수 없도록 데이터베이스 제약도 추가했다.

적재 작업은 새 버전을 계산하기 전에 같은 값이 이미 있는지 확인한다.

```text
같은 값이 있음  → 기존 버전의 세 결과가 남아 있는지 확인 → 기존 행 수 반환
같은 값이 없음  → 다음 버전 계산 → 세 결과 저장 → 값과 버전 기록
```

기존 버전을 재사용할 때도 버전 이력만 믿지 않는다. 기사별 한 달 운행 실적, 기사별 추천 차량 결과, 입력 데이터 이력이 모두 한 행 이상 남아 있는지 데이터베이스에서 다시 센다. 이력만 있고 실제 결과가 없다면 성공으로 처리하지 않는다.

새 결과와 버전 이력은 기존과 같이 하나의 트랜잭션에 기록한다. 세 결과의 행 수 검사가 끝난 뒤에만 버전 이력을 추가한다.

이미 운영 중인 데이터베이스에는 새 컬럼이 없으므로 별도 마이그레이션 SQL을 추가했다. 과거 버전은 당시 입력과 설정을 복원할 수 없어 `legacy-version` 값으로 구분했다. 이후 적재부터 SHA-256 값을 기록한다. 마이그레이션을 다시 실행해도 같은 unique constraint를 중복 추가하지 않는다.

## 적용 전후 비교와 검증

| 구분 | 적용 전 | 적용 후 |
|---|---|---|
| 커밋 후 응답 유실 | 재시도에서 다음 버전 생성 | 기존 성공 버전과 행 수 반환 |
| 입력이 바뀌지 않은 수동 재실행 | 다음 버전 생성 | 기존 버전 재사용 |
| 입력 버전 또는 추천 설정 변경 | 다음 버전 생성 | 다음 버전 생성 |
| 중복 방지 기준 | 없음 | 운영 지역·대상 월별 SHA-256 unique constraint |
| 기존 버전 | 식별 값 없음 | 겹치지 않는 과거 버전용 값으로 백필 |

자동화 테스트에서는 다음을 확인했다.

- 입력과 추천 설정이 같으면 결과 행 순서를 바꿔도 같은 64자리 SHA-256 값이 나왔다.
- 정제 데이터 경로나 추천 임계값을 바꾸면 다른 값이 나왔다.
- 첫 호출이 커밋된 상태에서 같은 요청을 다시 호출해도 bulk insert 호출은 3회에서 늘지 않았고 버전 1만 남았다.
- 입력 경로를 바꾼 뒤 호출하면 bulk insert 호출이 6회로 늘고 버전 2가 추가됐다.
- 재사용 분기를 고의로 끄자 같은 회귀 테스트에서 bulk insert 호출이 6회로 늘어나 실패했다.
- 분기를 원복한 뒤 최종 데이터 적재 관련 테스트 19개가 모두 통과했다.

실제 PostgreSQL을 실행하는 통합 테스트는 이번 변경에 포함하지 않았다. 현재 테스트는 데이터베이스의 상태와 SQL 응답을 모사한다. 실제 제약과 트랜잭션 동작을 확인하는 통합 테스트는 별도 작업에서 다룬다.

동시에 시작한 두 최초 실행이 같은 다음 버전을 고르는 경쟁 조건도 이번 범위에는 포함하지 않았다. 같은 작업의 순차 재시도는 기존 버전을 재사용하지만, 동시 실행 제어는 별도 잠금 작업에서 처리할 예정이다.

## 결론

데이터베이스 반영 이후 성공 응답이 유실돼도 같은 입력과 설정으로 새 버전을 만들지 않게 바꿨다. 입력 버전이나 추천 설정이 달라질 때만 다음 버전을 저장한다.

중복 여부는 작업 실행 번호가 아니라 실제 계산 입력으로 판단한다. 따라서 자동 재시도와 같은 입력의 수동 재실행에 같은 규칙이 적용된다.
